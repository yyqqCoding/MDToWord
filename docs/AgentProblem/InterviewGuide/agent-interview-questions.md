# AI Agent 开发面试问题与解决方案

这不是零散故障日志，而是一份面向面试的高价值问题库。问题来自常见面经，也从 MD To
Word 反馈修复 Agent 的真实设计中提炼。答案优先说明本项目的做法；项目尚未实现的能力
会明确标注为“通用/未来方案”，不把设想说成现状。

## 一、项目架构与工程取舍

## 问题：1. 请介绍这个 Agent 项目解决什么问题？

### 解决方案：

MD To Word 是一个 Markdown 到可编辑 Word 的转换产品。用户通过扩展提交“导出失败或
结果不符合预期”的反馈，Agent 判断是否属于后端转换缺陷，固定源码版本，在隔离沙箱中
生成回归测试、尝试最小后端修复，独立验证后创建 Pull Request；功能需求和前端问题则
创建脱敏 Issue。

项目的重点不是让模型自由写代码，而是把不可信反馈转换为可审查、可恢复、可追踪的
工程变更。

## 问题：2. 为什么使用 Agent，而不是一次大模型调用或固定工作流？

### 解决方案：

一次调用适合信息抽取和简单问答，但代码修复需要搜索不同文件、观察测试结果、调整候选
补丁，下一步取决于上一步的真实结果。固定工作流能保证安全，但面对不同缺陷时探索能力
不足。

本项目采用折中方案：外层使用确定性的 LangGraph 管业务阶段，内层使用一个受限的
ReAct Agent 选择查询、编辑和沙箱工具。模型只拥有有限的探索自由，状态、权限、验证和
发布仍由本地代码控制。

## 问题：3. 为什么保留 LangGraph，又引入 create_agent？

### 解决方案：

LangGraph 擅长持久化业务状态、条件路由、checkpoint 和恢复；这些步骤不能由模型临时
决定。create_agent 擅长在一个阶段内循环调用工具，模型可以根据 JUnit 或源码结果选择
下一步，不必预先输出一份僵硬的完整计划。

因此 LangGraph 是外层业务编排器，create_agent 是 repair_agent 节点内部的执行器，两
者不是重复框架，而是分别承担确定性和探索性。

## 问题：4. 一次反馈的完整链路是什么？

### 解决方案：

入口保存反馈并限流，Scheduler 原子领取后启动 Gate。Gate 无工具地完成分类和安全路由；
后端 Bug 才固定 GitHub main 的 base_sha，执行 conversion probe，再进入 Repair Agent。

Agent 在沙箱中证明基线失败，产生修复候选并验证；外层重新执行目标、全量测试和 DOCX
结构检查，最后创建 PR。功能或前端反馈不进入代码修复，而进入脱敏 Issue；越权、无关或
信息不足的反馈直接进入相应终态。

## 问题：5. 哪些工作交给模型，哪些必须由确定性代码完成？

### 解决方案：

模型适合做语义判断、选择要搜索的符号、设计回归测试、提出结构化编辑，并根据测试结果
继续迭代。确定性代码负责路由兜底、路径和补丁白名单、状态转换、预算、Sandbox 命令、
最终验证、脱敏和 GitHub 写入。

原则是：模型提供候选，受信代码提供权限和证据。模型说“已修复”不算成功，只有验证
Artifact 和状态机认可的结果才算成功。

## 问题：6. 为什么要先做 conversion probe？

### 解决方案：

用户反馈大致分两类：转换过程直接抛错，或者转换成功但 Word 结果不符合期望。前一类的
回归测试可以由 Controller 根据受信异常固定生成；后一类需要 Agent 结合反馈设计 DOCX
语义断言。

先探测可以避免让模型仅凭原文猜测错误类型，也能让“错误修复”和“结果修复”使用不同
的证据标准。probe 只判断转换是否抛错，不替代最终 DOCX 验证。

## 问题：7. 为什么前端问题不让 Agent 直接修改 extension？

### 解决方案：

当前自动修复目标是后端转换链路，自动 PR 的写入白名单只包含两个后端实现文件、回归
测试和反馈固件。扩展的修改会影响发布渠道、用户兼容性和权限边界，不能因为模型认为
“改前端更容易”就越过审查。

Gate 将前端/扩展问题路由为 issue_required，由维护者决定是否单独开发。这个范围限制
既减少风险，也让自动修复的成功标准足够清晰。

## 问题：8. 为什么当前只使用一个 Repair Agent？

### 解决方案：

项目运行在 2H2G 主机，Sandbox 本身串行；当前任务的主要复杂度来自工具探索和测试反馈，
不是角色数量。拆成规划、编码、审查多个 Agent 会增加通信、上下文同步、权限和调试成本，
并不能自动提高正确率。

单 Agent 加受限工具已经能形成完整闭环。未来只有当任务类型、权限或资源确实需要隔离
时，才考虑多 Agent，并且仍由受信 Supervisor 控制边界。

## 问题：9. 为什么 Scheduler 只处理一个任务？

### 解决方案：

单并发能保护 2H2G 主机上的模型、数据库和 Docker 资源，也避免多个修复同时基于不同
main 生成冲突补丁。它还简化了租约、幂等和人工排障。

如果未来提高并发，应先把 Worker 资源池、任务优先级、base_sha 冲突和全局预算设计清楚，
不能只把线程数调大。

## 问题：10. Supabase、checkpoint、Artifact 和 Langfuse 为什么分开？

### 解决方案：

Supabase 保存业务事实：反馈、run 状态、阶段、终态和发布 URL。checkpoint 保存内层
工具消息和恢复位置，Artifact 保存源码快照、patch、JUnit 和 DOCX 结果，Langfuse 只保
存脱敏的模型/工具观测。

这样可以分别控制查询性能、恢复能力、文件大小和隐私风险。Trace Site 读取 Supabase
的业务摘要，不能用 Langfuse 的缺失来推断业务阶段没有执行。

## 二、ReAct、控制流与状态

## 问题：11. ReAct 的完整流程是什么？

### 解决方案：

ReAct 把任务拆成“根据当前上下文选择 Action，执行工具得到 Observation，再决定下一
步”。在本项目中，模型的 Action 是 search_source、read_source_file、提交结构化编辑、
run_sandbox 或完成工具；Observation 是脱敏源码片段、JUnit 摘要和错误信息。

模型不能直接执行 Python 或写文件。工具函数把结果写入 checkpoint，下一轮模型再依据
真实结果行动。

## 问题：12. 为什么不用先生成完整 Plan JSON？

### 解决方案：

完整计划在模型真正读取源码和运行测试前往往是假设，遇到测试参数错误、缺少前置产物或
基线结果变化就会失效。让模型每步观察后再决定下一步，能减少无效计划和不必要的字段
兼容。

本项目仍然保留结构化工具参数和本地 Policy，而不是退回自由文本；变化的是控制粒度，
从“模型一次输出全计划”变为“模型逐步调用受限工具”。

## 问题：13. Loop 和 DAG 如何取舍？

### 解决方案：

有明确顺序和强业务约束的步骤适合 DAG，例如 Gate、源码快照、最终验证和发布。需要根
据观察动态探索的步骤适合 Loop，例如搜索不同函数、修正测试和尝试候选补丁。

本项目把两者组合：外层是带条件边的 Graph，内层是有预算和终态的工具 Loop。不是所有
步骤都交给 Loop，也不是把每一步模型调用都硬编码成节点。

## 问题：14. Agent 如何避免死循环和重复调用？

### 解决方案：

本项目有模型调用预算、工具调用预算、Sandbox 总时长和 Graph recursion limit 四层
保护；完成工具和 report_blocked 是明确出口。ToolMessage 会告诉模型缺少的前置动作，
避免重复提交同一个无效请求。

还应记录工具签名、阶段和结果 hash，发现相同动作连续重复时提前停止或转人工。预算是
失控保护，不是证明任务成功的条件。

## 问题：15. LangGraph 的 State、Node、Edge 分别负责什么？

### 解决方案：

State 是跨节点传递的结构化运行事实；Node 执行一个受信业务动作；Edge 决定下一步，
Conditional Edge 根据已校验状态路由到不同分支。

外层 State 保存 route、phase、base_sha、验证和发布信息，内层 State 保存消息、工具
阶段、patch 引用、测试结果和累计用量。模型文本不能直接覆盖这些关键字段。

## 问题：16. checkpoint 如何实现断点续跑？

### 解决方案：

每轮模型/工具动作后保存 checkpoint。进程重启时，Scheduler 从数据库恢复 run 和租约，
Repair Agent 使用同一个 repair:<run_id> thread 读取最后状态，复用 base_sha、Artifact、
patch 引用和累计预算继续执行。

恢复不能把计数清零，也不能重新创建已完成的 Sandbox、PR 或 Issue。若 State 结构不兼容，
应结束旧 run 并用新反馈重新验收，而不是猜测旧 checkpoint 的含义。

## 问题：17. 如何区分模型的“完成”与真实完成？

### 解决方案：

普通文字回复不是终态。complete_reproduction 必须有基线按预期失败的受信结果，
complete_repair 必须有当前目标 Sandbox 通过；工具函数还要检查 patch 引用、phase 和
必需字段。

即使内层完成，外层仍执行独立 final validation。只有验证通过才允许 Publisher 创建
PR 或 Issue。

## 问题：18. 为什么同一个工具在不同阶段要动态开放？

### 解决方案：

复现阶段允许提交测试，不允许提交修复；修复阶段允许提交后端补丁，不允许重写测试。
没有 patch 时可以编辑，有待验证 patch 时主要开放 Sandbox，通过后只开放完成工具。

阶段工具策略既减少模型误操作，也让工具描述更短。执行函数内部仍要二次校验，不能只
依赖模型当前看到的工具列表。

## 问题：19. 工具并行调用如何设计？

### 解决方案：

只读的 search_source 和 read_source_file 没有副作用，可以在同一模型响应中并行执行。
补丁写入、Sandbox、完成工具和发布动作会改变状态或消耗资源，必须单独一轮。

本项目的并行只优化源码查询延迟，不增加 Sandbox 并发；Worker 仍然串行。若未来支持
更多并行，应为每个状态字段定义合并策略，防止写冲突。

## 问题：20. Summary 和 checkpoint 有什么区别？

### 解决方案：

checkpoint 是恢复所需的受信结构化事实和原始消息存档；Summary 是模型上下文过长时的
压缩文本，目的是让下一轮继续理解任务。Summary 丢失时可以从 checkpoint 重建，不能用
Summary 代替预算、验证结果或 Artifact。

本项目的 Summary 必须保留目标、用户要求、事实、已完成证据、失败原因、下一步、禁止
事项和未确定事项，并明确标记没有证据的内容。

## 三、工具调用与权限

## 问题：21. Function Calling 的完整链路是什么？

### 解决方案：

模型先根据工具描述生成名称和参数，框架解析成 tool call；本地代码再做 Schema、阶段、
路径、预算和状态校验，校验通过后执行工具，把结构化结果作为 ToolMessage 返回模型。

本项目不会把工具调用直接映射为 Shell。run_sandbox 的命令、Job ID、源码快照和容器限制
都由 Controller 构造，模型只能提供简短原因。

## 问题：22. 工具 Schema 如何设计才稳定？

### 解决方案：

参数应表达一个清晰动作，使用枚举、长度上限和结构化字段，避免同时允许命令字符串、
任意字典和自由路径。错误响应也要结构化，包含 error_code、reason 和 required_action，
让模型知道下一步怎么修正。

Schema 只能表达字段形状；跨字段规则、权限和业务前置条件必须由本地 Policy 再检查。
工具名称和描述应包含何时使用、不能做什么和一个简短例子。

## 问题：23. 本地 Policy 是什么？

### 解决方案：

Policy 是受信代码里的确定性授权层，不是第二个 Agent，也不是只写在 Prompt 里的建议。
它决定当前路由、允许的工具、路径和补丁白名单、预算、Sandbox 前置条件及发布资格。

Prompt 负责让模型理解任务，Policy 负责真正放行动作。模型即使声称有权限，也不能改变
Policy 的决定。

## 问题：24. 工具错误应该怎样返回给模型？

### 解决方案：

可修正错误应返回短而可执行的 ToolMessage，例如“缺少 test_patch_ref，下一步调用
submit_test_edits”。字段、阶段和 required_action 要明确，避免只返回“执行失败”。

参数错误和缺少前置产物可以在同一 run 修正；越权、认证、安全和未知编程错误不应该让
模型反复尝试。

## 问题：25. 为什么读写白名单要分开？

### 解决方案：

诊断需要看到更多上下文，但自动修改范围必须更小。当前可以只读相关 backend Python
文件和测试，自动写入只允许 normalizer、pandoc_runner、反馈回归测试和固件。

这样模型可以理解调用关系，又不能把 extension、依赖、配置、Agent 或部署文件放进 PR。
扩大白名单需要维护者审查，不由模型根据一次反馈自我授权。

## 问题：26. 结构化编辑为什么不直接让模型生成 unified diff？

### 解决方案：

模型直接生成完整 diff 容易出现错误路径、上下文漂移和隐藏的额外修改。项目让模型提供
search_replace 或受限 full_file 编辑，Workspace 在固定 base_sha 上应用并用 Git 生成
确定性 patch。

这样可以检查唯一命中、重叠编辑、文件范围、增删行数、hash 和 git diff --check，后续
Sandbox 和 Publisher 只信任生成后的 patch。

## 问题：27. 缺少前置产物时为什么不直接暂停人工？

### 解决方案：

如果只是模型还没有先提交 test.patch 或 fix.patch，这是可恢复的流程错误，不是安全事件。
工具返回 tool_precondition_failed 和 required_action，模型在同一循环补齐前置动作，减少
人工重跑。

如果请求越过白名单、试图执行未注册工具或修改安全配置，则是不可恢复的越权，应立即
security_rejected。

## 问题：28. 如何防止 Prompt Injection？

### 解决方案：

不要把“扫描到某个关键词”当作唯一防线。用户反馈、源码、测试日志和工具输出都明确标
记为数据；Gate 不开放工具，Repair Agent 只看到当前阶段工具，所有参数再经本地 Policy
和 Sandbox 限制。

即使注入内容诱导模型读取密钥或改扩展，模型也没有对应工具；Sandbox 无网络、无 Secret，
Publisher 也不对模型开放。

## 问题：29. 为什么工具结果也要当作不可信输入？

### 解决方案：

测试输出、源码注释或外部 API 响应可能包含“忽略之前规则”的文字。若把它们直接拼进系统
提示词，模型可能误把观察结果当指令。

本项目返回结构化、有限、脱敏的 ToolMessage，并由本地状态决定下一步。需要保留完整证据
时放入受控 Artifact，而不是把大段内容永久塞进上下文。

## 问题：30. 如何控制有副作用的工具？

### 解决方案：

把副作用工具拆成“生成候选”和“受信执行”两层。模型只能提交 patch 或请求 Sandbox，
真正的文件物化、数据库更新、GitHub 发布由 Controller/Publisher 处理。

对不可避免的外部写入使用幂等键、状态检查和审计记录；超时恢复时先查询是否已经成功，
再决定是否重试，避免重复 PR、Issue 或消息。

## 四、Sandbox 与安全工程

## 问题：31. 为什么代码 Agent 必须放进沙箱？

### 解决方案：

模型生成的测试和代码无法被宿主机视为可信，即使任务来自正常用户，也可能有死循环、
恶意导入、任意文件读取或资源消耗。沙箱把执行权限限制到临时 workspace 和固定命令，
即使测试失败也不会直接影响 Controller、数据库和凭据。

本项目使用独立 Sandbox Worker 和新建临时容器；Worker 串行执行并在任务结束后销毁
workspace。

## 问题：32. Sandbox Worker 和 Controller 如何分工？

### 解决方案：

Controller 持有业务状态、模型和 GitHub 边界，只构造经过校验的 Job；Worker 只负责认证
Job、启动受限容器、执行固定 argv 和返回结构化结果。Worker 不知道业务凭据，也不接受
模型传来的命令、工作目录或环境变量。

这种分工让代码执行面和业务写入面隔离，Worker 出问题时也不会自动获得发布权限。

## 问题：33. 一个安全的任务容器需要哪些限制？

### 解决方案：

至少要使用固定镜像 digest、非 root、只读根文件系统、无网络、丢弃 Linux capabilities、
禁止新增权限、CPU/内存/PID 限制、临时可写目录和固定入口。还应关闭 pytest 外部插件
自动加载，禁止 pip install、下载源码和访问云元数据。

本项目还不把 Docker Socket、宿主机敏感路径、模型密钥、数据库 URL 或代理变量挂进
任务容器；每个任务完成后销毁容器。

## 问题：34. 为什么不能让模型直接传 pytest 命令？

### 解决方案：

命令字符串会带来 shell 注入、任意测试、任意工作目录和资源绕过。项目让模型只调用
run_sandbox 并填写 reason，Controller 根据已登记的 Job 类型和测试选择器构造 argv，
Worker 再次校验。

测试选择器先通过安全正则，并作为独立参数传递，不能经 shell 拼接。

## 问题：35. 如何设计源码读取白名单？

### 解决方案：

先区分读取和写入权限，再按业务需要列出最小目录。读取只开放相关 backend Python、
测试、项目摘要和规则文件；拒绝绝对路径、路径穿越、仓库外符号链接、密钥和构建产物。

工具先搜索再按行读取，限制单文件和单次结果大小。读取白名单只能帮助诊断，不能推导出
写入权限。

## 问题：36. Patch Policy 应该检查什么？

### 解决方案：

执行前检查路径规范化、白名单、文件数量、增删行数、patch 字节数、文本编码、二进制、
符号链接、权限变化、重命名、重叠编辑、测试与修复路径互斥和 git diff --check。

还要确认修复没有删除或弱化新增测试，Artifact hash 与实际文件一致。任何越界补丁直接
进入安全终态，不靠模型解释放行。

## 问题：37. 如何保护 Secret 不被模型和日志泄露？

### 解决方案：

凭据只注入对应的受信适配器进程，使用 Secret 类型配置并禁止写入消息、State、Artifact、
日志、Trace、PR、Issue 和容器环境。日志和观测先做字段白名单与敏感模式扫描。

不要通过工具参数传密钥，也不要把完整 HTTP 异常、环境变量或 Authorization 头直接回传
模型。调试时记录错误类型和请求 ID，不记录 Secret 值。

## 问题：38. 数据投毒和提示词注入如何区分？

### 解决方案：

提示词注入是输入试图改变 Agent 指令或权限；数据投毒是长期把错误反馈、错误轨迹或
低质量标注写进评测、Prompt 或记忆，导致系统以后持续变差。两者都不能只依赖关键词
过滤。

本项目把用户、源码和工具结果视为不可信，注入反馈不进入修复。若未来建立数据飞轮，
还应使用受信标签、来源、版本、审核状态和离线评测门禁，未经确认的数据不能自动改
Prompt 或 Policy。

## 问题：39. 为什么允许模型读源码，却不允许它改所有源码？

### 解决方案：

读权限用于定位根因，写权限直接影响生产。后端转换缺陷可以限定在 normalizer 和
pandoc_runner；扩展、配置、依赖、Agent 和部署文件的改动需要维护者另行开发。

这是一种最小权限和可审查原则：让模型看到足够证据，但让潜在错误的影响面保持很小。

## 问题：40. 如何处理外部 API 或工具的副作用？

### 解决方案：

优先把副作用操作放到受信适配器，模型只提交意图；操作使用幂等键、超时、状态查询和
审计日志。超时恢复时先查询请求是否已成功，不能简单再次发送。

对于无法回滚的动作，应在执行前要求人工确认或使用补偿事务。当前项目的 PR/Issue 由
Publisher 负责，模型没有外部写入入口。

## 五、失败归因、重试与恢复

## 问题：41. Agent 的错误为什么要做细粒度归因？

### 解决方案：

只记录“运行失败”无法判断是模型超时、工具参数错误、源码凭据失效、沙箱不可用还是
补丁越权，也无法决定是否安全重试。项目统一记录 kind、code、component、operation、
phase、node、attempt、handling 和脱敏 safe_details。

这样运行页能指到具体阶段和位置，运维可以按策略恢复，评估也能统计真实失败分布。

## 问题：42. 如何区分 provider_unavailable 和 invalid_response？

### 解决方案：

provider_unavailable 表示请求没有得到可用响应，例如超时、连接断开或上游 5xx；它可能
在相同输入下再次成功。invalid_response 表示已经收到响应，但严格 Schema 或本地 Policy
不通过，例如字段路径不合法；它不是网络重试问题。

前者进入有限传输重试，后者返回字段级修正提示或停止。两类错误不能使用同一个模糊
错误码，否则会把永久问题当成网络抖动。

## 问题：43. 外部模型超时应该怎样重试？

### 解决方案：

先定义可安全重发的错误和幂等边界，再使用指数退避、最大次数和总超时。当前模型一轮
最多三次总 attempt：主模型、等待 1 秒、主模型、等待 2 秒、备用模型。只对 timeout、
连接异常、408、429、5xx 重试。

认证、权限、安全拒绝、上下文超限、Schema/Policy 错误和未知编程异常不做盲目重试。每
次 attempt 都记录位置和处理决定。

## 问题：44. 为什么重试次数是三次，而不是无限重试？

### 解决方案：

无限重试会阻塞队列、放大费用并掩盖配置错误。三次给短暂网络抖动一次恢复机会，同时
通过 1/2 秒退避控制请求节奏；第三次切备用模型后仍失败就明确终止。

三次是单个模型轮次的上限，不是整个 Agent 运行只能调用三次模型。整个运行还由持久化
model/tool budget 和 Sandbox 时长限制。

## 问题：45. 备用模型应该何时切换？

### 解决方案：

备用模型用于主模型的可重试传输失败，不应在业务结果失败时盲目切换。当前是主、主、
备用三次总 attempt，并且主备都必须具备完整的 OpenAI-compatible profile、tool calling
和上下文窗口配置。

对外仍按统一 Provider 口径记录，实际接口信息只保留在受控诊断中，避免业务逻辑绑定
具体供应商。

## 问题：46. Sandbox 超时或连接失败怎么处理？

### 解决方案：

只有相同 Job 输入可安全重发时才重试。当前 Sandbox 临时连接、408、429、5xx 最多三次，
复用同一 job_id、请求指纹和幂等键，退避 1 秒和 2 秒；已经完成的结果直接复用。

401、409、非法请求、无效 200、容器安全拒绝和参数错误不重试。Worker 串行运行，避免
重试和并发容器同时耗尽 2H2G 资源。

## 问题：47. 哪些错误绝对不能重试？

### 解决方案：

认证失败、越权、安全拒绝、配置缺失、上下文超限、非法工具调用、无效补丁和未知编程
异常都不应按网络失败重试。业务测试不通过通常进入下一轮候选，但不能重复执行同一个
明显无效动作。

判断依据应来自稳定错误类型和代码，而不是错误消息是否包含“暂时”或模型的文字解释。

## 问题：48. 失败发生在不同层时如何定位？

### 解决方案：

Adapter 负责把厂商协议、HTTP 状态和本地异常转换为稳定 code、kind、component 和
operation；Graph 节点再补充 phase 和 node。这样适配器不需要知道自己被哪个 Graph 节点
调用，也不会把业务知识渗进底层。

最终日志同时关联 run_id、attempt、处理策略和安全细节，能区分模型、工具、Sandbox、
源码、验证和发布错误。

## 问题：49. 进程重启后如何继续任务？

### 解决方案：

数据库保存外层 run 和租约，checkpoint 保存内层 repair:<run_id> 工具循环。恢复时读取
最后 checkpoint，保留 base_sha、patch 引用、Sandbox 结果和累计预算，不重新领取一个
全新任务。

外部副作用通过 job_id、patch hash 和 PR/Issue marker 幂等复用。旧 token 失效后不能
覆盖新进程的结果。

## 问题：50. budget_exhausted 应如何处理？

### 解决方案：

模型调用、工具调用、Sandbox 时长和 Graph recursion limit 分开计数。达到任一上限就写入
budget_exhausted，停止继续调用，不把历史计数清零。

维护者可以检查最后的失败原因和候选补丁，调整配置后使用原 run ID 显式恢复。自动重开
容易重复副作用，也会让成本失去上界。

## 问题：51. stale_base 是什么，为什么不能直接 rebase？

### 解决方案：

Agent 基于 base_sha 生成并验证补丁；发布时如果 main 已变化，旧补丁可能把新的业务
修改覆盖或产生隐蔽冲突。因此 stale_base 触发既有一次性重排，重新获取快照、复现和验证。

不让模型自行 rebase 是为了重新获得基线失败和修复后通过的证据；超过重排限制则转人工。

## 问题：52. 失败记录里哪些细节可以公开？

### 解决方案：

公开或 Langfuse 只放错误类型、字段路径、阶段、节点、attempt、处理决定、计数、耗时和
有限脱敏尾部。完整源码、用户 Markdown、联系方式、命令、Token、完整 traceback 和
校验器内部文案留在受控 Artifact 或本机日志。

尤其 invalid_response 的安全细节只保留 schema error path，不把可能含用户数据的校验
提示上传 Trace。

## 六、测试、修复与代码 Agent

## 问题：53. 为什么修复前必须先证明基线失败？

### 解决方案：

如果测试在基线就通过，模型可能是在修复一个不存在的问题，或者测试根本没命中用户
场景。基线失败把用户反馈转化为可执行证据，也能防止“修复后通过”这种循环论证。

本项目要求先在固定 base_sha 的新 Sandbox 运行测试，再允许进入 repairing。

## 问题：54. 如何测试“转换成功但结果不符合预期”？

### 解决方案：

需要把用户期望翻译成稳定的语义 Oracle，例如 DOCX 文本、样式、公式 XML 节点或部件
结构，而不是依赖截图或模型自评。测试应在基线失败、修复后通过，并尽量覆盖不会被误
判为成功的反例。

如果期望只涉及主观视觉、当前没有受信断言，应转 needs_human，而不是生成脆弱测试。

## 问题：55. 转换直接报错时为什么由 Controller 固定生成测试？

### 解决方案：

转换异常已经由受信 probe 确认，错误类型和复现输入是确定的。Controller 固定生成最小
回归测试，比让模型重新解释异常更稳定，也避免模型输出复杂的 Oracle。

模型仍然需要读取源码并生成修复；固定测试只是减少复现阶段的不确定性。

## 问题：56. 修复 Agent 如何选择下一步？

### 解决方案：

先搜索和读取相关源码，再提交最小测试或修复，运行 Sandbox，依据结构化结果继续调整。
这是 ReAct 的“Action–Observation”循环。模型不能跳过基线、独立验证或发布前检查。

工具返回失败时必须说明字段和 required_action，让模型纠正，而不是只返回一个无法行动
的“失败”。

## 问题：57. 为什么修复补丁要尽量小？

### 解决方案：

小补丁更容易审查、回滚和归因，也降低引入无关回归的概率。项目通过写入白名单、文件
数量、增删行数、patch hash 和测试保护限制影响面。

如果根因需要重构、依赖或扩展改动，不应强行塞进自动 PR，应转 Issue 或人工开发。

## 问题：58. 目标测试通过后为什么还要跑全量测试？

### 解决方案：

目标测试只证明一个反馈场景被修复，可能掩盖其他 Markdown、表格、公式、Mermaid 或
后端 API 的回归。独立全量测试验证补丁没有破坏既有行为。

本项目还检查 skipped 数量、编译、DOCX 部件和 hash，避免通过删除测试或改变测试环境
伪造成功。

## 问题：59. 为什么最终验证要在新的 Sandbox 中完成？

### 解决方案：

同一 workspace 可能被测试运行时修改，模型也可能留下未声明的文件。新容器从固定快照
重新应用已校验 patch，可以验证补丁本身，而不是验证上一轮的偶然环境。

最终验证由外层 Graph 的受信节点执行，模型不能调用或跳过它。

## 问题：60. 如何防止模型通过修改测试“修复”问题？

### 解决方案：

测试补丁和修复补丁路径互斥，修复阶段不开放测试提交；Patch Policy 拒绝删除、跳过、
放宽断言或修改测试基础设施的行为。最终验证还会重新检查测试文件和 workspace diff。

人工审核 PR 时也要看测试是否真正描述用户行为，而不是仅检查函数返回非空。

## 问题：61. 什么情况下应判定 cannot_reproduce？

### 解决方案：

当测试无法稳定收集、基线不能按预期失败、用户期望缺乏可验证 Oracle，或者问题已经被
当前 main 修复时，不能为了生成 PR 强行继续。

应保留测试尝试、失败类型和安全摘要，终态为 cannot_reproduce 或 needs_human，并用于
后续评估，而不是发布空补丁。

## 问题：62. 如何验证一个自动生成测试是高质量的？

### 解决方案：

看四点：是否命中用户输入、是否在基线稳定失败、是否表达必要的语义、是否有反例避免
过宽断言。还要检查测试离线、确定、无 Secret、无外部网络，并且不会污染仓库。

可以让人工抽样审阅测试，也可以离线运行“测试扰动”或变异测试，观察断言是否真的能
检测回归。

## 问题：63. 代码 Agent 的成功标准应该是什么？

### 解决方案：

不是模型输出一段看起来合理的代码，而是“基线失败、补丁应用、目标通过、全量无回归、
DOCX 结构正确、权限和 hash 正确、PR 脱敏”。每项证据都由受信工具或验证节点产生。

最终状态和错误原因要能被页面、日志和 Artifact 互相对照。

## 问题：64. 如何减少修复失败后的人工介入？

### 解决方案：

把可恢复的流程错误返回给同一 ReAct 循环，例如缺少 test_patch、行号错误和测试参数
错误；把网络瞬态错误按幂等策略重试；只有越权、认证、预算、无法复现和持续验证失败才
转终态或人工。

同时保留精确 FailureSnapshot，让维护者能用原 run 显式恢复，而不是重新提交反馈。

## 七、Prompt、结构化输出与评测

## 问题：65. Prompt 优化除了增加约束规则，还有哪些方法？

### 解决方案：

先改善任务分解和信息顺序，再使用少量高质量示例、明确的工具描述、失败反馈和输出
模板。还可以减少无关上下文、把规则移到确定性代码、调整模型和温度，并用真实 badcase
做 A/B，而不是不断堆“必须”。

本项目的关键做法是 Prompt 与本地 Policy 同步：Prompt 解释怎样行动，Policy 真正拦截
越权和错误状态；工具错误会把可执行修正返回模型。

## 问题：66. 如何保证模型返回的 JSON 合规？

### 解决方案：

使用 Provider 支持的严格 Structured Output 和 Pydantic Schema，让字段类型、枚举、必填
项由接口校验；收到响应后再做本地 Policy 和跨字段校验。不要只用正则解析自然语言
里的 JSON。

校验失败时区分“没有收到有效响应”和“收到但字段不合法”，记录字段路径，把可执行的
修正反馈给模型；永久无效时停止，不能无限格式重试。

## 问题：67. Schema 很严格会不会限制真实错误类型？

### 解决方案：

Schema 应描述稳定的动作和字段形状，而不是提前穷举所有业务错误。当前复现/修复通过
工具参数表达编辑和阶段，具体失败由 Sandbox 结果和本地 Policy 返回。

对开放问题保留有限枚举加安全摘要，不让模型传入任意 XPath、回调或动态参数字典。
稳定的新业务能力应新增受信工具或 Oracle，而不是把 Schema 做成任意 JSON。

## 问题：68. Prompt 中写了规则，为什么还需要本地 Policy？

### 解决方案：

Prompt 是模型的行为指导，模型可能误解、遗漏或被用户内容影响；Policy 是代码执行前
的硬边界。路径白名单、工具可见性、预算、状态跳转、补丁和发布权限不能靠模型自律。

跨字段规则要在两处保持一致，并为 Prompt 版本、Policy 版本和校验错误建立可观测记录。

## 问题：69. 如何设计一次 Prompt A/B 评测？

### 解决方案：

固定反馈样本、模型、温度、工具和预算，只改变一个 Prompt 版本；每个案例重复多次，统计
路由准确率、工具选择、基线复现、修复通过、越权拒绝、Token 和耗时。

本项目使用独立 evaluation Provider，不消耗生产主/备模型额度，不写生产 Trace 或发布
数据。通过门槛后才升级生产 Prompt。

## 问题：70. 评测集从哪里来？

### 解决方案：

包括正常成功案例、真实 badcase、错误输入、无关反馈、Prompt Injection、权限越界、
超时、Schema 失败和回归案例。每个案例要有输入、预期路由、允许工具、关键证据和终态，
而不是只保存最终答案。

生产运行可脱敏回流为候选样本，但进入黄金评测集前要有人审核标签和期望结果。

## 问题：71. 如何定位是模型、Prompt、Policy 还是工具的问题？

### 解决方案：

把一次轨迹拆成 Gate、模型 generation、tool call、ToolMessage、Sandbox 和验证结果。若
模型没有选择工具，可能是 Prompt 或工具描述；若选择正确但参数被拒绝，是 Schema/
Policy；若执行结果不对，是工具、Sandbox 或业务代码。

FailureSnapshot 和稳定命名的 Trace 让这些层可以按 run、phase、node 和 attempt 对齐，
避免只看最终失败文字。

## 问题：72. 如何处理模型返回格式错误后的重试？

### 解决方案：

先保留字段路径和安全的结构化错误，给模型一次明确修正机会；同时保留原始响应在受控
日志中供排查。格式纠正和网络传输重试要分开计数，不能因为 Schema 错误连续重发同一
请求。

如果修正后仍无效，进入 invalid_response 或 needs_human，并记录模型版本和 Prompt 版本。

## 问题：73. 如何选择主模型和备用模型？

### 解决方案：

先用代表性结构化生成、工具调用和长上下文案例评测质量，再权衡延迟、成本、上下文窗口、
稳定性和隐私。备用模型必须支持同一工具协议和足够的输入窗口，否则无法安全接管。

本项目主备都使用 OpenAI-compatible 接口；配置 audit 和 model-smoke 会检查 profile、
tool calling、缓存字段和 Summary 行为。

## 问题：74. 如何降低模型幻觉？

### 解决方案：

减少让模型凭空判断的空间：给出最小相关源码、真实 Sandbox 结果和结构化状态；要求先
调用工具再下结论；用测试和独立验证作为成功标准；无法证明时允许拒答或转人工。

代码 Agent 不应只让模型自评“修复完成”，而要用基线/目标/全量测试、DOCX 断言和 patch
Policy 形成证据闭环。

## 问题：75. 温度、top-p 和采样参数如何影响 Agent？

### 解决方案：

工具调用和结构化修复通常需要稳定性，先使用较低随机性并通过评测确定；探索性内容
可以适度提高温度。不要只凭经验改参数，应同时观察成功率、重复动作、Token 和延迟。

更重要的是工具边界、反馈质量和验证机制；采样参数不能修复错误的状态机或安全策略。

## 问题：76. 为什么真实模型评测不能替代自动测试？

### 解决方案：

真实模型评测验证模型能力、Provider 协议和 Prompt 效果，但成本高、结果有随机性，不能
覆盖所有错误分支。Fake Provider 的自动测试负责稳定验证状态、权限、重试、预算和幂等。

本项目先跑离线 Fake 和专用评测，再用少量可丢弃真实数据做手工全流程验收，二者互相
不能冒充。

## 八、上下文工程、缓存与记忆

## 问题：77. Context 和 Memory 有什么区别？

### 解决方案：

Context 是当前任务为了下一步决策临时提供的信息；Memory 是跨轮次或跨任务保存、可再
检索的信息。前者强调及时和相关，后者强调来源、作用域、版本、置信度和过期。

本项目用 checkpoint 保存当前工具循环，用 Artifact 保存证据，不把所有历史轨迹当作
长期记忆。未来增加记忆时应先定义用途和删除策略。

## 问题：78. 长上下文超过模型窗口怎么办？

### 解决方案：

先减少无关信息，再分层保留任务目标、硬约束、可信事实、未完成事项和失败证据；大源码
和日志放 Artifact，按需 search/read，不一次塞入上下文。

本项目在有效窗口 65% 触发 Summary，保留最近 20%；总结后仍达到 85% 就停止，避免模型
在截断上下文上继续猜测。

## 问题：79. Summary 必须保留哪些内容？

### 解决方案：

至少保留目标、用户要求、可信事实和引用、已完成事项及证据、当前结构化状态、失败尝试
与原因、下一步、禁止事项和未确定事项。没有受信验证的结论要标记为未确认。

Summary 不能写 Secret、联系方式、完整源码、完整 patch 或大段日志，也不能覆盖 checkpoint
中的预算、验证和 Artifact 引用。

## 问题：80. KV Cache 和业务缓存有什么区别？

### 解决方案：

KV Cache 是模型推理过程中对已处理 token 的中间表示缓存，通常依赖固定前缀和 Provider
实现；业务缓存保存请求、工具结果或 Artifact，生命周期和一致性由应用控制。

本项目通过稳定的系统 Prompt、工具描述和 Summary 结构帮助 cache 命中，但不能把 Provider
返回的 cache_read_tokens 当作业务正确性证据。

## 问题：81. 工具结果太长时如何处理？

### 解决方案：

工具返回有限的结构化摘要、行号、失败类型和必要尾部；完整结果存受控 Artifact，模型
需要时再按范围读取。对于 JUnit、日志和源码都应设置字节上限和分页/分段策略。

不要简单截断错误关键行，也不要把所有输出永久放进 Summary；应保留 hash 和引用保证
可回放。

## 问题：82. 如何防止 Summary 把错误事实带到下一轮？

### 解决方案：

把受信状态和模型摘要分开保存；总结只压缩消息，不直接写入验证结果、预算、patch 或
终态。提示词要求区分“已验证”和“模型推测”，并在下一步工具执行前重新检查关键前置。

如果 Summary 质量异常，硬限制停止并从 checkpoint/Artifact 重建，而不是继续使用错误
上下文。

## 问题：83. 什么时候需要长期记忆或向量库？

### 解决方案：

只有跨任务重复使用的稳定知识、用户偏好或经验案例才值得进入长期记忆；单次源码、日志
和 patch 更适合 Artifact。长期记忆需要来源、权限、版本、置信度、过期和删除机制。

本项目当前没有把修复轨迹自动写入长期记忆。未来可以将人工确认的高质量案例做成评测
或检索资料，但不能让未经审核的轨迹直接改变行为。

## 问题：84. 为什么上下文工程不只是裁剪 token？

### 解决方案：

真正目标是让下一步决策拿到正确、最新、最少但足够的证据。包括信息分层、来源标注、
工具结果格式、失败反馈、摘要时机、缓存前缀和恢复引用。

只做字符截断可能丢掉禁止事项或失败证据，反而增加工具循环和成本。

## 九、可观测性、部署与成本

## 问题：85. Agent 为什么要做全链路 Trace？

### 解决方案：

最终答案只告诉你成功或失败，不能说明模型为什么选择工具、哪一次请求超时、哪个补丁
被拒绝。Trace 要把 Gate、模型 generation、tool call、Sandbox、验证和发布按同一 run
关联起来。

本项目用稳定的 feedback-repair-run 根和 phase/node 字段组织轨迹；Supabase 保存业务
状态，Langfuse 只保存脱敏 observation，Artifact 保存完整受控证据。

## 问题：86. 线上失败日志至少应该记录哪些字段？

### 解决方案：

至少记录 run_id、phase、node、component、operation、稳定 error_code、kind、attempt、
max_attempts、handling、耗时、模型/工具计数和安全 safe_details。这样可以回答“在哪一
步、为什么、做了什么决定、还能否恢复”。

不要为了调试把完整反馈、源码、Token、Authorization、完整 traceback 或测试日志写入
公开日志。

## 问题：87. 如何设计 Agent 的核心指标？

### 解决方案：

分路由看接受率、拒绝/安全隔离率、Issue/PR 生成率；分阶段看复现成功率、修复成功率、
最终验证通过率、重试和恢复成功率；分资源看 Token、cache、模型耗时、Sandbox 耗时和
成本。

指标必须有清晰分母，并区分模型失败、工具失败、业务无法复现和安全拒绝，不能只报一个
“Agent 成功率”。

## 问题：88. 如何做成本和延迟控制？

### 解决方案：

使用单任务模型/工具预算、总 Sandbox 时长、上下文阈值、结果裁剪和有限重试；只读查询
并行，副作用动作串行。通过 cache、稳定 Prompt 前缀和更小的相关源码范围减少输入。

优化前先按 phase 分解耗时，判断瓶颈在 Provider、上下文、工具、Sandbox 还是发布，不能
用无限 timeout 掩盖问题。

## 问题：89. 生产 Agent 如何部署和更新？

### 解决方案：

公开转换后端部署在 Render；Controller/Scheduler 和 Sandbox Worker 在独立 Linux 主机，
Worker 只监听本机端口。更新时先 disable 自动领取，再拉取 main、运行 deploy.sh、audit
和 model-smoke，维护者确认后输入 ENABLE。

脚本失败时保持 Scheduler 关闭；代码版本、依赖、Worker 认证和真实反馈验收都要检查，
不能只看 systemd active。

## 问题：90. model-smoke 和真实全流程分别验证什么？

### 解决方案：

model-smoke 使用合成消息，验证主/备模型 profile、tool calling、只读并行、usage/cache、
Summary 65%/85% 阈值，不读取真实反馈、不启动 Sandbox、不写 GitHub。

真实全流程使用可丢弃后端反馈，验证源码快照、基线复现、修复、独立全量/DOCX 验证和
PR/Issue 脱敏。前者不能替代后者，后者也不能替代自动测试。

## 问题：91. 如何做 Agent 的灰度、回滚和版本管理？

### 解决方案：

把 Graph、Prompt、Policy、工具 Schema、State Schema 和 Sandbox image digest 都写入运行
元数据。先在离线评测和少量可丢弃反馈上比较，再逐步开启生产领取。

发现错误时停止 Scheduler，回滚代码/镜像或恢复旧配置；活动 run 不应在未知 schema 上
继续猜测，必要时结束并重新验收。

## 问题：92. 如何设计可观测的人工接管？

### 解决方案：

人工接管应有明确触发：越权、安全、低置信度、无法复现、预算耗尽、持续验证失败、
stale_base 超限或外部凭据错误。页面显示失败位置、建议动作和是否可用原 run 恢复。

人工处理结果可以作为评估标签，但不能未经审核直接改变 Prompt、Policy 或白名单。

## 十、通用能力与未来演进

## 问题：93. 什么是数据飞轮，如何从一条用户反馈开始？

### 解决方案：

数据飞轮不是“把所有日志喂给模型”，而是一个受控闭环：

~~~text
用户反馈
  -> 脱敏和分类
  -> 运行轨迹、测试/修复结果和人工结论
  -> 形成带来源的候选案例
  -> 人工或规则审核标签
  -> 离线评测 Prompt/Policy/模型
  -> 通过门禁后上线
  -> 新运行继续产生反馈
~~~

本项目已有反馈、FailureSnapshot、Sandbox 证据和 PR 结果，适合先做评测数据集；当前不
自动修改生产 Prompt 或代码。每条案例要有输入摘要、预期路由、错误位置、最终结果、
版本和审核状态。

## 问题：94. 自进化和普通日志分析有什么区别？

### 解决方案：

日志分析只回答发生了什么；自进化还要把高质量案例转成可验证的改进候选，例如 Prompt
版本、工具描述、Policy 规则、评测样本或代码补丁，然后通过离线门禁比较新旧版本。

真正的闭环必须允许“不改进”：如果新版本没有在固定评测集上提升，候选就不发布。当前
项目应先做人工确认的 Prompt/评测迭代，暂不让模型自改权限和白名单。

## 问题：95. 如何防止数据飞轮被数据投毒？

### 解决方案：

把原始反馈、模型推测、工具证据和人工标签分层保存；记录来源、时间、版本、审核者和
置信度。注入、无关和敏感数据不直接进入修复数据集；若要保留，只能进入隔离的安全/
意图识别对抗评测集，用来改进 Gate Prompt 和分类 Policy，而不能用来训练修复策略。

候选改进必须在固定黄金集、回归集和安全集上比较，人工批准后才能更新生产。数据量少
的个人项目也需要这个最小门禁，否则一条错误反馈就可能长期污染行为。

## 问题：96. 多 Agent 什么时候值得引入？

### 解决方案：

只有当任务可以清晰拆成不同权限/专业能力，且通信、状态一致性和成本收益明确时才引入。
例如规划、执行和审查需要不同凭据，或者任务可以独立并行。

当前项目用一个 Repair Agent 已足够；增加多个角色会带来上下文同步、冲突、循环和调试
成本。未来若引入，应由受信 Supervisor 控制工具、预算和终态，不能让子 Agent 无限派生。

## 问题：97. Skill 和 MCP 分别解决什么问题？

### 解决方案：

Skill 更像可发现、可复用的任务方法和约束集合；MCP 是工具/资源接入协议。Skill 可以
编排多个 MCP 工具，但二者都不应绕过本地权限和 Sandbox。

本项目当前没有引入通用 Skill 或 MCP Server，工具直接由 create_agent 注册并由 Policy
控制。若未来增加，应先定义版本、触发条件、输入输出和安全验收。

## 问题：98. Agent 需要 RAG 吗？

### 解决方案：

RAG 适合从大量外部知识中检索事实；当前代码修复 Agent 主要读取固定源码快照和测试，
使用受限 search/read 已满足需求，盲目接入向量库会增加权限、版本和数据新鲜度问题。

未来若需要跨仓库文档或历史案例，可采用带版本和权限过滤的检索，并保留来源引用；关键
代码事实仍应以固定快照和测试结果为准。

## 问题：99. 如何把用户反馈转成可训练或评测的案例？

### 解决方案：

先脱敏，再把反馈与 run、base_sha、错误快照、测试 patch、修复 patch、验证结果和人工
结论关联。不要只保存模型最终文本，要保存“基线为何失败、候选为何失败、最终为何通过”。

按路由、错误类型、代码区域和难度分层，避免成功案例过多导致评测失真。样本进入黄金
集前由人工确认标签和 Oracle。

## 问题：100. Agent 系统中哪些内容不应自动化？

### 解决方案：

权限扩大、修改依赖/部署/扩展、合并 PR、生产 Schema migration、处理敏感数据、改变
安全策略和把候选 Prompt/Policy 发布到生产，都应保留维护者确认。

自动化的边界不是越大越先进，而是每一步都有可验证证据、可回滚路径和明确责任人。
个人项目也可以用“自动执行低风险、人工审批高风险”的方式保持完整闭环。

## 问题：101. 如果重新设计这个项目，最先优化什么？

### 解决方案：

先补齐失败可观测性和评测集，再优化 Prompt、工具描述和上下文；随后根据真实瓶颈改进
模型、缓存或并发。不要一开始就引入多 Agent、长期记忆、RAG 或自动自进化。

本项目当前最有价值的工程能力是权限控制、隔离执行、基线/修复/独立验证和可恢复错误
归因；扩展应围绕这些事实积累，而不是堆框架名词。
