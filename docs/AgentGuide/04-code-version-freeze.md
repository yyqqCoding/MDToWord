# 04 · 把代码"锁死"在一个版本上

> 上一章([03](03-gate-classification.md))里,安检把一条反馈判成"正经后端 Bug",放进了自动修复链。
> 这一章讲进修复链后的**第一件事**:去 GitHub 把 main 分支的源码整个复制一份只读副本,记下当时
> 的提交号 `base_sha`。为什么必须这么做?看完你就懂。

## 1. 一句话:先造一台"时光机"

假设 AI 今天根据用户描述,写了一条测试说"这段代码会坏"。你修到第三天,期间 main 分支已经被人
改过了——那"它确实会坏"这个结论还成立吗?**不一定。** 别人可能刚好把那段代码重写了,Bug
已经没了,或者挪了位置。

所以进修复链的第一件事不是看 Bug,而是先**把当前 main 分支的整份源码下载一份副本**,钉在当前
那个提交号上,记作 `base_sha`。**这次修复的全部工作——复现、改代码、验证——都在这份固定副本上
进行。**

好处有两个,都跟"可信"有关:

1. **证据能自洽**:你说"这代码会坏"和你说"我修好了",测的是同一版代码。谁也别想偷偷换版本,
   让"修好"变成幻觉。
2. **追溯有锚点**:每次运行都记着它当时钉在哪个提交上。以后翻旧账,永远能知道这次跑的是哪一版。

## 2. 这份副本到底是什么:快照(snapshot)+ 大件仓库(Artifact)

系统把这份固定副本叫**快照(snapshot)**,它不只是一堆文件,而是三样东西绑在一起:

| 东西 | 人话 | 记在哪 |
|---|---|---|
| **归档包** | GitHub 打的整份源码压缩包(`.tar.gz`),下载下来 | 磁盘上 run 目录里 |
| **base_sha** | 这个快照对应的 40 位提交号(main 当时的脑袋) | 运行记录、数据库 |
| **校验和(sha256)** | 对归档包算的哈希。以后每次要用前都重新算一遍比对 | 快照的元数据 |

为什么要带校验和?因为这份归档是**从网络下载的不可信输入**(还记得原则吧:凡是从外面进来的都
当它可能被篡改)。万一下载损坏或被中间人动过手脚,一比对哈希就露馅。而且下载过程本身也写得
很小心:

- 先看快照元数据在不在——如果进程上次崩了、这次是续跑,就不重新下载,直接用上次那份
  (保证一次运行永远只用同一份副本);
- 下载到一半中断了怎么办?用**临时文件 + 原子改名**,磁盘上不会留下半个文件;
- 解压时逐个文件检查:路径不允许有 `.`、`..`、`.git`,不允许有符号链接/硬链接/设备文件——
  防止压缩包里有坏东西在解压时越出目录、访问主机文件;
- 解压先解到临时目录,全部成功后再"原子改名"成正式目录。任何一步失败,整份作废重来,
  不会留一份"缺胳膊少腿"的快照在那。

## 3. 白名单:AI 只能看到和改到什么

快照到手后,得先决定一件事:**让 AI 读哪些文件、改哪些文件?** 这台机器改的是真仓库,不能让它
在整份源码里乱逛乱写。于是本地守则划了一张**白名单**(机器可读,写在 `patch_policy.json`):

**可以读(白名单内)**:后端转换的核心 Python 源码(`backend/app/` 下)、后端测试(`backend/tests/`)、
几个项目说明文件。其余(部署脚本、前端、历史、秘密相关)一律不开放。

**可以改(分两类,更窄):**

| 阶段 | 能改哪 | 举例 |
|---|---|---|
| **复现**(写测试) | 一个固定回归测试文件 + 测试固件目录 | `backend/tests/test_feedback_regressions.py`、`backend/tests/fixtures/feedback/` |
| **修复**(改代码) | **后端两个文件** | `backend/app/normalizer.py`、`backend/app/pandoc_runner.py` |

注意这个反直觉的点:**AI 能"读"的面比能"改"的面宽得多。** 它可以读整片 `backend/app/` 来理解
代码,但真正动手写修复,只许落在那两个文件上;还有个 `mermaid_renderer.py` 是可读不可写的受信
模块。写测试只能追加到那一个回归测试文件(如果文件已非空,只能在一个固定"锚点"后面追加,
不能乱改已有的测试)。这些都是**本地写死**的规则,AI 改不了、工具也扩不了。

> 你可能想问:白名单这么窄,会不会想改的文件不在里面、于是修不了?会。但这是**故意的取舍**:
> 宁可让"问题出在白名单之外"的反馈进不了自动修复链(它会被转人工),也不让 AI 获得越界的写
> 权限。自动修复只解决最核心那两三个文件能解决的问题。

## 4. 顺手建一个"测试基座"

有了锁死的源码,还不能立刻让 AI 复现——得先给它准备一个"往哪写测试"的落点:

- 那份唯一能改的回归测试文件 `test_feedback_regressions.py`,如果之前已经存在(别的 Bug 修过、
  里面已有回归测试),系统会把它的"当前状态 + 唯一尾部锚点"记下来,告诉 AI:"新测试只能在这
  个锚点后面追加";
- 用户提交的那段原始 Markdown,会按规则存成一个**测试固件(fixture)文件**(比如
  `backend/tests/fixtures/feedback/xxx.md`),供测试读取。

> 为什么要固件而不是把用户原文硬塞进测试代码里?因为原文是**不可信输入**,直接拼进 Python
> 源码既不安全也不整洁;存成独立固件文件,测试只负责"读文件、跑转换、断言结果"。

## 5. 这一章的流程图

```text
安检判定:正经后端 Bug
   │
   ▼
prepare_source 节点:
   │  ① 读 main 当前提交号(base_sha)── 记下这一刻
   │  ② 从 GitHub 下载整份源码压缩包 ── 带大小/内容/路径安全检查
   │  ③ 算 sha256 校验和,全部成功才落盘(原子改名)
   │  ④ 把 base_sha + 快照引用 写进运行记录
   ▼
建立白名单视野(读) + 落点(唯一回归文件 + 固件目录)
   │
   ▼
交给下一章的主角:Repair Agent(复现 + 修复)
```

## 6. 本章出现的关键词速查

| 词 | 人话 | 对应代码/位置 |
|---|---|---|
| base_sha | 钉住的 40 位提交号,main 当时的脑袋 | `SourceSnapshot.base_sha` |
| 快照(snapshot) | 一份只读的整源码副本 = 归档 + base_sha + 校验和 | `agent/workspace/source_repository.py`、`preparation.py` |
| 校验和(sha256) | 用前必验的哈希,防下载被篡改/损坏 | `source_snapshot_sha256` |
| 白名单 | 本地守则规定 AI 能读/能改的文件清单 | `agent/policies/patch_policy.json` |
| 回归测试文件 | 唯一能写测试的地方(只能尾部追加) | `backend/tests/test_feedback_regressions.py` |
| 修复白名单 | AI 修代码只能改后端两个文件 | `normalizer.py`、`pandoc_runner.py` |
| 测试固件 | 用户 Markdown 原文存成的只读数据文件 | `backend/tests/fixtures/feedback/` |
| Artifact / 引用 | 大文件(快照、补丁、日志)的仓库;运行状态只存引用路径 | `agent/workspace/artifacts.py` |

下一章是整份指南最重的一章:**唯一让 AI 自由发挥的地方**——复现与修复(Repair Agent)。
