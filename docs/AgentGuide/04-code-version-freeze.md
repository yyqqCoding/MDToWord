# 04 · 源码快照与版本固定设计

本章说明后端自动修复开始前，系统如何固定源码版本并建立工作边界。核心设计是：一次处理
运行（run）只使用一个不可变源码基线，复现、修复、终验和发布都引用这个基线，而不是在
持续变化的主分支上反复取最新代码。

本文首次引入的术语如下：主分支（main）是 GitHub 中作为修复基准的分支；基础提交标识
（base_sha）是该分支当前提交的 40 位 SHA-1 标识；源码快照（source snapshot）是与该提交
绑定的源码归档和校验元数据；制品存储（Artifact）保存快照、补丁和测试结果等大对象；补丁
策略（Patch Policy）是规定读写路径和补丁规模的本地受信规则；隔离执行环境（Sandbox）用
于运行测试，外层流程状态（Graph State）保存可恢复的结构化进度。

## 1. 为什么必须固定 base_sha

如果复现和发布期间直接读取 `main`，同一条反馈可能产生以下不一致：

```text
基线测试在提交 A 上失败
修复测试在提交 B 上通过
发布时补丁针对提交 C
```

此时无法判断测试和修复是否针对同一个问题。固定 `base_sha` 后，一次运行的证据链变成：

```text
base_sha
  -> 源码快照
       -> 测试补丁
       -> 修复补丁
       -> Sandbox 执行
       -> 独立验证
       -> 发布前重新物化
```

这样可以保证：

- 基线失败确实发生在待修复的版本上；
- 修复通过与基线失败具备可比性；
- 验证结果和最终发布内容可以通过哈希对账；
- 历史运行可以根据 `base_sha` 复查当时使用的源码。

固定版本并不意味着可以忽略最新代码。发布前仍要重新读取 `main` 的当前提交；如果它已经
不同，系统进入 `stale_base`（基础版本过期）处理，不把旧基线上的补丁直接发布到新版本。

## 2. 源码快照的组成

源码快照不是单纯的目录，而是三个互相绑定的对象：

| 对象 | 作用 |
|---|---|
| 源码归档 | GitHub 根据 `base_sha` 生成的完整源码压缩包 |
| `base_sha` | 说明归档对应的确切提交 |
| `source_snapshot_sha256` | 对归档内容计算的 SHA-256（安全哈希摘要），用于完整性校验 |

Controller（控制器）在 `prepare_source` 节点完成快照准备。成功后，运行状态只保存源码快照
引用，后续工具和 Sandbox 根据引用取得同一份归档；大文件本身由 Artifact 管理，不直接塞入
外层 Graph State（流程状态）。

## 3. 快照取得与物化流程

### 3.1 取得固定版本

准备流程先读取 GitHub `main` 的当前提交，再根据这个提交取得源码归档。下载和保存遵循以下
顺序：

1. 若当前运行已有完整快照元数据，则复用已有快照，避免恢复时切换版本；
2. 新归档先写入临时文件，下载完成后计算 SHA-256；
3. 哈希、大小和元数据校验通过后，使用原子重命名写入正式位置；
4. 解压到临时目录，完成所有安全检查后，再原子重命名为正式工作区；
5. 将 `base_sha`、快照哈希和引用写入运行状态。

任意一步失败都不能留下可被后续流程误用的半成品。恢复时，如果元数据存在但归档或目录不
完整，系统应按快照错误终止或重新准备，而不是把不完整目录当作基线继续运行。

### 3.2 归档解压安全

源码归档来自外部服务，必须作为不可信输入处理。物化时至少拒绝：

- 绝对路径和包含 `.`、`..` 的路径穿越；
- `.git` 目录、符号链接、硬链接和设备文件；
- 超出大小限制、哈希不匹配或结构无效的归档。

这层检查防止归档在解压时写出目标目录，也防止快照中的 Git 元数据或特殊文件影响主机。

## 4. 读取范围与修改范围分离

快照准备完成后，本地策略（Policy）依据 `patch_policy.json` 建立两类边界：模型可以读取哪些文件，以及
候选补丁可以修改哪些文件。读取范围大于写入范围，是为了让模型能够理解调用关系，但不把
同等范围的修改权限交给模型。

### 4.1 允许读取的范围

当前允许读取：

```text
backend/app/**/*.py
backend/tests/**/*.py
backend/pyproject.toml
AGENTS.md
README.md
```

读取通过仓库相对路径和行范围执行。绝对路径、路径穿越、仓库外符号链接、敏感文件和超出
单文件/单次输出限制的请求都会被拒绝。

### 4.2 允许修改的范围

| 阶段 | 允许修改 | 目的 |
|---|---|---|
| 复现 | `backend/tests/test_feedback_regressions.py`，以及 `backend/tests/fixtures/feedback/` 下的固件文件 | 形成可重复的回归测试 |
| 修复 | `backend/app/normalizer.py`、`backend/app/pandoc_runner.py` | 修改后端转换实现 |

测试固件（fixture）是从反馈得到的、供测试读取的独立文本数据文件。它不应被拼接进 Python
测试源代码，以减少用户输入直接影响代码语法和测试结构的风险。

以下内容不属于自动修改范围：扩展、Agent 自身、依赖、Dockerfile、部署配置、数据库、凭据、
安全策略和其他受信平台模块。`backend/app/mermaid_renderer.py` 等可读但不可写的模块也保持
这个单向边界。

## 5. 测试基座与补丁来源

复现测试统一追加到 `test_feedback_regressions.py`。如果该文件已经存在，系统在准备阶段保存
其当前内容和唯一尾部锚点；模型只能在锚点之后追加，不能修改既有测试。这样做可以区分：

- 原有回归测试是基线的一部分；
- 本次测试补丁是当前反馈新增的证据。

模型提交的是结构化 Edit（编辑指令），不是可以直接执行的任意 diff。受信工作区应用 Edit
后生成补丁，并重新计算补丁哈希。后续 Sandbox、独立验证和 Publisher（发布器）只接受通过
Policy 校验且哈希一致的补丁制品。

## 6. 固定版本带来的取舍

| 选择 | 收益 | 代价 |
|---|---|---|
| 以 `base_sha` 固定完整源码 | 复现和验证结果可比较、可追溯 | 每次运行需要下载、保存和清理归档 |
| 归档哈希与原子物化 | 防止损坏或替换的快照进入执行面 | 准备流程更复杂，磁盘占用更高 |
| 读写白名单分离 | 保留理解代码所需的上下文，限制修改面 | 某些跨文件修复必须转人工 |
| 固定回归文件和尾部追加 | 防止模型改写已有测试 | 测试组织灵活性降低 |

这些代价是有意接受的。自动修复的目标是生成可审核的候选，而不是覆盖所有可能的源码变更；
超出白名单的问题应当明确转人工，而不是扩大模型权限。

## 7. 阶段时序

```text
accepted_backend_bug
  -> prepare_source
       读取 main 当前提交
       -> 取得源码归档
       -> 校验大小、路径和 SHA-256
       -> 安全解压并生成 source snapshot
       -> 保存 base_sha、快照引用和元数据
  -> 建立测试文件锚点与反馈 fixture
  -> 进入修复代理（Repair Agent）的复现/修复循环
```

## 8. 实现关联

| 能力 | 主要实现 |
|---|---|
| 快照下载与完整性校验 | `agent/workspace/source_repository.py`、`agent/workspace/preparation.py` |
| 快照和补丁制品 | `agent/workspace/artifacts.py` |
| 读取白名单 | `agent/workspace/paths.py`、`agent/workspace/validation.py` |

| 测试锚点与编辑应用 | `agent/workspace/edits.py` |
