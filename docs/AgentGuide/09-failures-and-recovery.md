# 09 · 出错与恢复:机器怎么"扛得住、摔不坏"

> 前面八章讲的是"一切顺利"时一份反馈怎么走完全程。但真实世界不会那么配合:网络会抖、模型会
> 一时糊涂、进程会被杀死、GitHub 会拒绝、容器会超时、钱会烧到上限……
>
> 这一章讲这台机器**为"出岔子"做的整套保险**:怎么给失败分类、什么该重试什么不该、进程死了
> 怎么从存档点接着干、预算烧完怎么收场、以及哪些失败**必须留给人**。

## 1. 一句话:机器把"失败"当成一等公民来设计

设计一台自动处理系统,最容易犯的错是"默认一切顺利,失败当异常处理"。这台机器反过来:**它默认
任何一步都可能失败,然后把"失败怎么处理"设计进每一步。**

这带来几个贯穿全系统的习惯:

- 每一步都有**存档(checkpoint)**,死了能续跑;
- 失败先**分类**——"网络抖了一下"和"权限不够"完全是两回事,处理方式必须不同;
- **只重试值得重试的**,其余诚实认栽;
- 花销有**上限**,绝不无休止烧钱;
- 最后还有一条底线:**机器搞不定的,明说,留给真人。**

## 2. 给失败分类:五种"病",五种治法

机器内部把失败分成五种**种类(kind)**,每种对应一种处理态度:

| 种类 | 人话 | 例子 | 处理态度 |
|---|---|---|---|
| **transient(一时抽风)** | 网络/服务"抖了一下",过会儿可能自己好 | 模型服务暂时不可用、限流、仓库暂时连不上 | **值得重试**:等一小会儿再来 |
| **invalid(输入/格式不对)** | 数据或格式本身不合法,重试也没用 | 模型回了个格式错的表、测试写得不合规 | **打回重写**:不是"再来一次"能解决的 |
| **business(业务不通过)** | 正常跑,但结果在业务上不成立 | 目标测试没绿、全量有回归、复现不出来 | **认栽**:记录结果,按流程收场(见第 6 章) |
| **security(安全被拒)** | 发现有人/有代码越界、想动手脚 | 容器工作区被动过、工具越权 | **立刻关闸**:谁也不碰,直接终止 |
| **permanent(永久失败)** | 配置错了、凭据坏了,重试一万次也没用 | GitHub 令牌失效、状态机跳到非法迁移、存档格式不兼容 | **别重试**:转人工,查配置 |

> 为什么分类这么重要?因为**对失败的处理方式,取决于它的种类,而不是它的样子**。同一个报错
> 窗口,背后可能是"网络抖一下"(该重试)也可能是"令牌过期了"(重试也没用,只会反复撞墙)。
> 分类错了,要么白白重试烧钱,要么该重试的没重试导致任务卡死。

这个分类**不是模型做的**,也不是运行时现猜的——它是一张**写死的对照表**:每个错误码对应一个
种类(代码里 `_KIND_BY_CODE` 那张表)。没登记的错误码会**安全降级**成"永久失败"——宁可保守
认栽,不冒险无限重试。

## 3. 两种重试,别搞混

### 3.1 短传输重试:给"一时抽风"用的

对 transient 失败,系统有套**写死的重试策略(RetryPolicy)**。它决定"能不能重试"要同时满足四个
条件,缺一不可:

1. 失败种类是 **transient**(一时抽风)——invalid / business / permanent 一律不在这重试;
2. 这次操作**幂等**(重做一遍不会有副作用,比如"查一下有没有已存在的 PR");
3. 预算**还没花完**;
4. 尝试次数**没到上限**(最多 3 次),且退避时间不会超出本次操作的总时限。

重试间隔也写死:**1 秒 → 2 秒 → 4 秒……指数退避,封顶 10 秒**。第 5 章讲过,模型调用层是
"主→主→备用"各试,车间传输是 3 次——它们都属于这种"短传输重试",纯粹是"电话没打通再拨一次",
**不是给 AI 更多试错机会**(那属于第 5 章的轮数预算)。

### 3.2 长流程重试:给"进程死了"用的

transient 之外,还有一类更粗粒度的恢复:**一次运行跑到一半,进程整个死了**(被杀、宕机、断电)。
这不能靠"等几秒重试"解决,要靠**存档点续跑**——下一节专门讲。

## 4. 存档点(checkpoint):每一步都存一档,死了接着跑

### 4.1 外层:LangGraph 的存档点

外层流水线每走完一个节点,就把当前进度**存进 PostgreSQL**(基于 LangGraph 的 checkpointer)。
存的是这张"运行小卡片"(AgentState):现在到哪个节点了、有了哪些存档引用、用了多少预算。

于是进程死了之后,下次醒来只需要:

```text
Scheduler 醒来
   │
   ├─ 数据库里有没有"没跑完的旧运行"?── find_resumable()
   │        │  有 → 恢复它:从存档点接着跑,不从头再来
   │        └  没有 → 认领一条新反馈
   ▼
```

恢复时,Scheduler **先找没跑完的旧运行,再领新任务**——旧运行优先,免得它一直占着
claimed/reproducing 的状态没人管。恢复不是重跑整个流程,而是**从断点继续**:已完成的模型调用、
已跑过的容器、已提交的补丁,全都不会重来一遍。

> 注意外层和内层是**两套各自的存档**,但**共享同一个数据库**:
> 外层 LangGraph 用一条 thread,内层 repair_agent 用独立 thread(`repair:{run_id}`),
> 它们靠 run_id 关联。外层节点还没返回时,外层存档只记录进入节点前的累计值;真正精确的
> 内层计量,在崩溃时要从内层 checkpoint 里补回来——所以你会看到"失败终结"时系统去**合并**
> 外层 + 内层两边的计数,取单调最大值,保证账不错、钱不丢。

### 4.2 内层:create_agent 也在存

别以为只有外层有存档。AI 在车间里那个 ReAct 循环,**每一步也都存进同一个 PostgreSQL**。
这意味着即使 AI 试到一半进程死了,恢复后它**不会失忆**——还记得自己提交过哪些测试补丁、
哪些容器结果,从上次停下的地方继续,而不是重新开始空转。

### 4.3 恢复不是无限的:失败会被"终结"

存档点救得了"进程死了",但救不了"这条反馈注定跑不完"。如果恢复后还是失败,系统会走
**失败终结(Finalizer)** 这一步——它把外层、内层、异常三处的用量**合并**起来,给这次运行盖个
最终的失败戳。这么做的原因很实在:

> 不终结的话,Scheduler 会**无限恢复同一个节点**——每恢复一次就烧一次钱,永远不收敛。
> 终结 = 给这次运行一个**确定性结局**,让 Scheduler 可以放下它、去处理别的反馈。

## 5. 特殊恢复:哪些"失败"其实可以再给一次机会

有些失败虽然被记成了终态,但**性质上值得人工显式再救一次**。机器不会自动救,但维护者指定
run_id 时,可以恢复。Controller 的恢复逻辑里专门处理了几种:

| 情况 | 恢复方式 | 为什么不自动恢复 |
|---|---|---|
| **发布失败**(publication 系列错误) | 只重开发布节点——**不重跑模型和容器**,验证结论已固定,直接拿它再发一次 | 发布是"临门一脚",失败多半是 GitHub 抽风或网络,补丁和验证都还好好的,重跑纯浪费 |
| **预算耗尽**(budget_exhausted) | 维护者显式给 run_id,恢复原 thread、沿用已提交的补丁,从断点继续试 | 预算烧完说明 AI 没能收尾,自动重开会无限烧钱;得有人看了情况再决定 |
| 旧版中间件误分类的失败 | 兼容性恢复(见 controller 里的错误类型白名单) | 只针对历史遗留,新运行不会走 |

> 看出规律了吗:**凡是"自动恢复"都要满足"幂等、有界、不会烧更多钱"**;一旦恢复可能无限循环
> 或烧钱,就转人工。这跟第 8 章 stale_base"只自动重排一次"是同一个性格。

## 6. 还有一层保险:失败记录(可观测)

每次失败都会被记成一个**脱敏的 FailureSnapshot**,里面有错误码、种类、组件、操作、阶段、节点、
处理方式、第几次尝试……但**没有**可能泄密的正文(响应原文、源码、凭据一概不进)。

记录失败的是一个 **fail-open 的观察者**(FailureRecorder):观测系统(比如 Trace)自己挂了,
**不能反过来阻断业务的失败收口**——记录不了就只打条日志,绝不让"看不了病"变成"连病都治不了"。

## 7. 撞破预算:不是失败,是"刹车"

前面反复提到的预算耗尽,严格说**不是失败,是主动刹车**。系统在任何一步都可能撞到三块表:
模型调用次数、工具调用次数、容器总时长。撞破时,内层把原因转成一个稳定的
`BudgetExceededError`(区分是 model_calls / tool_calls / graph_steps 哪一种),外层走
`finish_budget_exhausted` 收场,给这次运行盖 **预算耗尽(BUDGET_EXHAUSTED)** 的戳。

预算耗尽后,那条反馈**不会自动再试**(见第 5 节)——除非维护者明确看了情况、给了 run_id 显式
恢复。这是"钱是有限的"这条铁律的落地:**AI 干活可以自由,但不能无上限地烧。**

## 8. 这一章的流程图

```text
任一步失败
   │
   ▼
归类:transient / invalid / business / security / permanent(写死的对照表)
   │
   ├─ transient + 幂等 + 有预算 + 未到上限
   │        └─► 短传输重试(1s→2s→4s…,封顶 10s,最多 3 次)
   │
   ├─ 进程死了
   │        └─► Scheduler 醒来先 find_resumable → 从存档点续跑(外层+内层共享数据库)
   │               └─ 恢复后仍失败 → Finalizer 终结,不再无限恢复
   │
   ├─ invalid → 打回重写;business → 按第 6 章收场;security → 关闸
   │
   ├─ permanent → 不重试,转人工 / 查配置
   │
   ├─ 发布失败 → 只重发(不重跑模型/容器),或 stale_base 重排一次
   │
   └─ 预算耗尽 → 刹车,盖 BUDGET_EXHAUSTED;维护者可显式恢复,不自动重开
```

## 9. 这一章出现的关键词速查

| 词 | 人话 | 对应代码/位置 |
|---|---|---|
| 失败种类(FailureKind) | transient / invalid / business / security / permanent 五种"病" | `agent/domain/failures.py` |
| 处理方式(FailureHandling) | transport_retry / format_revise / stale_requeue / stop…… | 同上 |
| 错误码→种类对照表 | 每个错误码对应一个种类,写死;未登记的安全降级 | `_KIND_BY_CODE` |
| 短传输重试 | 只给 transient、幂等、有预算、未超上限的失败 | `RetryPolicy.decide` |
| 存档点(checkpoint) | 外层每节点 + 内层每步都存 PostgreSQL,死了续跑 | 基于 Postgres 的 checkpointer |
| find_resumable | Scheduler 每轮**先找没跑完的旧运行**再领新任务 | `_claim_and_run` |
| 失败终结(Finalizer) | 合并外层+内层用量,给运行盖确定性失败戳,防无限恢复 | `controller._finalize_run_failure` |
| 特殊恢复 | 发布失败只重发;预算耗尽维护者显式恢复 | `controller.resume` |
| fail-open 记录器 | 观测系统挂了不能阻断业务收口 | `FailureRecorder` |
| 预算耗尽 | 主动刹车,不是失败;不自动重开 | `finish_budget_exhausted` |

到这里,主线旅程(安检 → 修复 → 验证 → 发布)和它的保险(出错与恢复)都讲完了。还剩三件
**横切全程**的事没讲:权限控制、隔离沙箱、可观测——下一章把它们一次讲清。
