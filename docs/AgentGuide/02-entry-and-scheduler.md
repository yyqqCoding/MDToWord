# 02 · 任务接收与调度设计

本章说明反馈如何从公开入口进入业务队列，以及后台如何在保证单任务所有权的前提下启动一次
处理。重点不是介绍某个接口的调用顺序，而是说明为什么要把“接收”“认领”和“运行”拆成
不同层次。

本文首次引入的术语会同时说明中文含义和代码中的名称：反馈接口（Feedback API）负责接收
用户提交；调度器（Scheduler）负责恢复活动任务和领取新反馈；控制器（Controller）负责启动
外层流程编排框架（LangGraph）；隔离执行环境（Sandbox）用于执行受信测试任务；执行工作进程
（Worker）负责启动 Sandbox；认领令牌（claim token）证明当前运行拥有反馈的更新权；认领租约
（lease）规定这项所有权的有效时间；处理运行（run）及其记录（AgentRun）表示一次完整处理
实例；代码合并请求（PR）和问题或需求单（Issue）是后续可能产生的 GitHub 协作对象。

## 1. 设计目标与职责边界

入口和调度层需要同时满足四个目标：

| 目标 | 设计要求 |
|---|---|
| 入口稳定 | 公开请求只做校验、限流和持久化，不调用模型或执行代码 |
| 所有权明确 | 同一条反馈在同一时间最多由一个运行更新 |
| 异常可恢复 | 处理进程退出后，任务不会永久停留在“已领取”状态 |
| 状态可追溯 | 反馈业务状态与某次运行的执行状态分别保存 |

因此，系统将职责分为三层：

```text
Feedback API
  -> 写入 Supabase（业务状态存储）中的 feedback 记录（status=pending）
       -> Scheduler 恢复旧 run 或领取新反馈
            -> Controller 启动外层 LangGraph 流程
```

公开入口不应直接连接模型、源码工作区或 Sandbox。这样可以把不可信的公网输入与后续高权限
执行面隔离，也避免一次请求占用长时间的处理资源。

## 2. 反馈接口：只登记，不处理

### 2.1 接收字段与持久化内容

接口接收 `feedback_type`、`markdown_content`、`description` 和 `contact` 等现有字段，
执行字段格式、长度和编码校验。通过校验后，反馈写入 Supabase（业务状态存储），初始状态为
`pending`（待处理）。写入时同时计算内容指纹（content fingerprint，即反馈内容的 SHA-256
摘要），供后续重复检测使用。

`contact` 只保留在反馈记录中供维护者联系用户，不进入模型输入、运行状态、日志、制品、沙箱
或代码合并请求/问题单（PR/Issue）。入口是隔离边界的第一层，而不是后续流程再尝试清理
联系方式的补救措施。

### 2.2 入口限流

当前入口使用单进程滑动窗口限流。默认限制如下：

| 维度 | 默认上限 |
|---|---:|
| 同一客户端 IP（Internet Protocol，客户端网络地址）每分钟 | 1 次 |
| 同一客户端 IP 每小时 | 5 次 |
| 同一客户端 IP 每天 | 10 次 |
| 所有客户端每小时 | 30 次 |

超过限制时返回 HTTP `429`（请求过于频繁），并通过 `Retry-After` 告知客户端建议等待时间，
但不暴露具体命中的规则或解析出的 IP。无法取得可信的公网 IP 时返回 `503`（服务暂不可用），
不使用代理地址或拼接的转发链作为限流身份。

这样设计有两个原因：限流身份必须稳定，否则恶意请求可能共享一个错误身份而绕过限制；限流
状态当前保存在入口进程内，因此实现简单，但不适合直接扩展为多实例共享限流。若部署拓扑变化，
应先更新权威运行文档和限流实现。

### 2.3 入口不做业务判断

以下动作明确不属于 Feedback API：

- 判断反馈是否是后端 Bug；
- 调用分类模型；
- 读取 GitHub 源码或启动 Sandbox；
- 创建 AgentRun、PR 或 Issue；
- 根据用户描述直接生成测试断言。

入口只生成待处理记录。分类和执行由私有调度器、控制器及其受信策略负责，后续章节从 [03 ·
反馈分类与路由](03-gate-classification.md) 开始说明。

## 3. 认领：为一次处理建立排他所有权

### 3.1 为什么不能直接读取 pending 记录

模型调用、容器执行和发布操作都可能产生成本或外部副作用。如果两个调度进程同时读取同一条
`pending` 反馈，就可能出现重复模型调用、重复修复和重复 PR。因此，读取队列和建立所有权
必须是同一个数据库原子操作，而不能拆成“先查询、再更新”两个请求。

### 3.2 数据库原子认领

调度器调用数据库中的认领函数（claim RPC，即由数据库执行的受控认领操作）。数据库以自己的
时钟判断租约，并在事务中完成以下步骤：

1. 从 `pending` 反馈中选择最早的一条；如果某条记录为 `claimed`（已领取）且租约已过期，
   也可以作为候选；
2. 使用行锁和 `FOR UPDATE SKIP LOCKED`（跳过已锁定行）避免并发调度器等待或选中同一记录；
3. 将 `attempt_count`（领取尝试次数）加一，写入 `claimed_at`（领取时间）和随机生成的
   `claim_token`；
4. 将反馈状态从 `pending` 或过期的 `claimed` 更新为 `claimed`；
5. 返回更新后的完整反馈记录。

认领函数同时检查 `max_attempts`（最大领取次数）。如果一条反馈已经达到上限且仍处于可认领
状态，数据库会将其转为 `needs_human`（需要人工处理），而不是继续进入自动队列。

### 3.3 claim token 的作用

`claim token` 是服务端随机生成的更新凭据。后续推进反馈状态、写入错误或记录发布结果时，
Repository（数据访问适配器）会将反馈 ID、当前状态和 claim token 一起作为条件；条件不匹配
就拒绝更新。

这是一种条件更新机制，主要解决两类并发问题：

- 旧运行因进程暂停，恢复后试图覆盖新运行的状态；
- 租约过期后，新运行已经取得了新的 token，旧运行仍继续提交结果。

因此，claim token 不是用户凭据，也不是模型可见信息，而是反馈记录当前所有权的内部版本标识。

## 4. lease：有限时长的所有权

### 4.1 为什么需要租约

如果进程在领取反馈后直接退出，数据库中可能只留下“已领取”状态。没有有效期时，任务会
永久占用，Scheduler 也无法判断能否安全接手。

租约将所有权定义为有限时间窗口：`claimed_at` 加上配置的 `lease_seconds` 后，当前认领失效。
数据库使用自身时钟判断是否过期，避免不同主机系统时间不一致导致误判。

### 4.2 租约过期后的处理

Scheduler 下一轮认领时可以重新选择租约已过期的 `claimed` 记录，但仍需通过以下条件：

- 反馈处于允许重新认领的状态；
- `attempt_count` 尚未达到 `max_attempts`；
- 数据库事务能够取得该行的锁。

重新认领会生成新的 claim token，旧 token 立即失效。租约只负责释放失联的所有权，不代表任务
一定可以无限重试；领取次数上限负责阻止永久循环，无法恢复的任务最终转人工。

## 5. 处理运行：记录一次完整执行实例

认领成功后，Controller 为本次处理创建 AgentRun（处理运行记录），生成全局唯一的 `run_id`。
运行记录至少需要保存：

| 信息 | 用途 |
|---|---|
| `feedback_id`、claim token | 关联反馈并验证更新权 |
| `graph_version`、提示词（Prompt）版本、本地策略版本 | 说明本次执行使用的流程和规则 |
| 当前阶段和运行状态 | 支持调度、页面展示和故障恢复 |
| 模型、工具、Token（模型计量单位）和 Sandbox 用量 | 预算控制、成本统计和验收 |
| 错误、验证结果、PR/Issue 地址 | 形成最终结果和审计索引 |

反馈记录和运行记录表达不同事实：

| 记录 | 表达的事实 |
|---|---|
| `feedback` | 用户这条反馈目前处于什么业务状态 |
| `agent_runs` | 某一次自动处理执行到了哪一步、产生了什么结果 |
| 私有 PostgreSQL 检查点（checkpoint） | 内层修复代理（Repair Agent）工具循环如何恢复 |

这种分离使业务页面不依赖完整模型消息，也避免上下文摘要覆盖业务状态。同一个反馈未来因
`stale_base`（基础版本过期）等原因重新排队时，可以产生新的运行记录，同时保留历史运行和
证据链。

## 6. Scheduler 的执行顺序

调度器每轮遵循“恢复优先、领取其次”的顺序：

```text
run_once
  -> 查找可恢复的活动 AgentRun
       -> 找到：使用原 run_id 和 checkpoint 继续
       -> 未找到：原子领取一条 pending/过期 claimed 反馈
            -> 创建或关联 AgentRun
                 -> 启动 Controller
```

恢复优先可以避免旧任务长期占用反馈状态。一次运行结束后，调度器记录终态并继续下一轮；
普通运行异常由 Controller 负责记录和终结，不能让常驻 Scheduler 进程退出。取消、终止等
进程控制信号不应被误记为普通业务失败，具体规则见 [09 · 失败处理与恢复](09-failures-and-recovery.md)。

## 7. 单并发的设计取舍

当前 Scheduler、Controller 和 Sandbox Worker 按单并发运行。原因不只是主机资源有限，更重要
的是源码修复的正确性：每个自动修复都基于一个固定 `base_sha`（主分支基础提交 SHA），并
可能创建补丁和 PR。多个任务同时进入修改和验证阶段，会增加源码版本漂移、资源竞争和发布
去重的复杂度。

单并发的代价是吞吐量较低，但换来了：

- 同一时间只有一个任务进入修复执行面；
- Sandbox 资源和模型预算更容易对账；
- 恢复、租约和发布幂等行为更容易验证。

如果未来需要提高吞吐量，应先重新设计共享限流、源码工作区、Worker 并发和发布幂等，不能
只把 Scheduler 线程数调大。

## 8. 端到端时序

```text
用户提交反馈
  -> Feedback API：校验、限流、保存 contact、计算内容指纹
  -> feedback(status=pending)
  -> Scheduler：恢复旧 run；无恢复项时调用数据库认领函数
  -> feedback(status=claimed, claim_token, claimed_at, attempt_count)
  -> 创建 agent_runs(run_id)
  -> Controller：校验 claim token，进入 gating
  -> 下一章反馈分类器（Gate）的分类与路由
```

## 9. 设计结论

入口、认领和运行记录分别解决三个问题：

1. 入口保证不可信请求以受限、可审计的形式进入系统；
2. 认领保证一条反馈的当前更新权只有一个有效持有者；
3. 运行记录保证一次处理可以恢复、计量和追溯。

后续流程不应绕过这三个边界，直接从反馈文本启动模型或执行任务。
