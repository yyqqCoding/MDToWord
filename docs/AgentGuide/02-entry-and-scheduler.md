# 02 · 入口与签收:一份反馈怎么进来、谁负责处理

> 上一章([01](01-feedback-life.md))讲了整段旅程。这一章讲最开头两件事:**反馈怎么存进数据库**、
> 以及后台的 **Scheduler 怎么把一个任务从"待处理"捞出来开始处理**。
>
> 本章要顺带讲清楚一组最容易把人绕晕的名词:**认领(claim)/ 认领牌(claim token)/ 保质期
> (lease)/ 一次运行(run)**。它们都围绕同一件事:"这个任务现在归谁管、管多久"。

## 0. 先记住一句话

> **反馈入口只负责"存",不负责"处理"。Scheduler 只负责"一次捞一个任务出来跑",不替模型做任何
> 判断。** 中间那个真正处理任务的是外层流水线(下一章开始讲)。

## 1. 入口 API:只做登记,不做聪明事

用户提交反馈时,请求打到后端一个公开接口上。这个接口**不做**任何"分析"——不调用模型、不
判断这是不是 Bug、不领任务。它只做四件"笨"事:

1. **格式校验**:该有的字段有没有、超不超长;
2. **限流**:防止有人刷接口。无登录入口最容易被人用脚本灌;限流按客户端 IP 计,比如"同一 IP
   一分钟最多 1 次 / 一小时 5 次 / 一天 10 次,全部 IP 一小时最多 30 次"。超了就回 429(请求
   太频繁),并告诉客户端"多久后再试",但不透露你命中了哪条规则、你的 IP 是什么;
3. **脱敏边界**:用户可能留了联系方式(方便人工沟通)。这个联系方式**只存在数据库这一行里**,
   从这一刻起不进任何后续环节——不进模型、不进日志、不进运行记录;
4. **写进数据库**,状态记为 **待处理(pending)**。入库同时算一个"内容指纹"(对反馈正文做哈希),
   以后可以用它识别"这条是不是重复反馈"。

一句话:**入口把反馈变成数据库里一行"待处理"的记录,仅此而已。**

> 一个值得知道的细节:入口无法可靠拿到"客户是谁"时,会直接拒绝(返回 503),而不是猜一个。
> 因为它限流要靠"谁是同一个客户"来判定,猜错就会放跑刷子或误伤好人——所以宁可收不到反馈,
> 也不做一个不可信的限流。

## 2. 为什么需要"签收"这套机制

数据库里的反馈不会自动被处理。处理它要花不少力气:要调模型、要在容器里跑代码、可能要发
PR——这些都是**有成本、有副作用**的动作。如果两个进程同时盯上同一条反馈,各自处理一遍,
结果就是重复烧钱、甚至发出两条一样的 PR。

所以需要一套机制保证:**一条反馈在同一时间最多只被一个进程处理。** 这就是"认领"。

## 3. 认领(claim):盖一个"归我管"的戳

后台有个常驻的轮询循环,叫 **Scheduler(轮询员)**。它每几秒醒来一次,**一次只处理一个任务**,
流程是:

```text
醒来
  ├─ 有上次没跑完的旧任务吗? → 有:接着把它跑完(恢复)
  └─ 没有 → 去数据库捞一条"待处理"的反馈 → 开始新任务
```

它捞任务的动作,在数据库层面是这样发生的(一次原子的 SQL 操作):

1. **挑一条**待处理的反馈(如果有多个进程并发,数据库用"跳过被锁定的行"保证大家挑到的是
   不同的反馈,不会抢同一件);
2. 给它写上:
   - `claimed_at`:认领时间(now);
   - `claim_token`:一个**随机生成的认领牌**;
   - `attempt_count` +1(这是第几次尝试处理这条);
3. 状态从"待处理"改成"**已认领(claimed)**";
4. 把这条记录原样返回给 Scheduler。

现在这条反馈身上带着一张**随机认领牌**。这张牌是后面所有操作的门票:**谁想改动这条反馈的
状态(推进到下一阶段、写错误、标记完成),都必须出示同一张牌**。数据库在改之前会对一下牌,
对不上就拒绝——这天然挡住了"两个进程抢同一任务"的局面:后到的人手里是旧的、已经失效的牌,
改不动。

> 换个生活化的比方:认领 = 前台给文件袋贴上"由 XX 处理"的便签,认领牌 = 文件袋的钥匙。
> 只有拿这把钥匙的人能打开袋子往里放东西。进程 A 拿到的钥匙,进程 B 用不了。

## 4. 认领牌(claim token)和保质期(lease)是配套的

你可能要问:**如果处理到一半进程崩了怎么办?** 那条反馈会一直卡在"已认领"吗?

不会,因为有**保质期(lease)**。认领时除了写时间,还隐含一个约定:**这次认领的有效期是有限的**
(代码里是一个以秒计的数值)。数据库的认领函数在"挑待处理任务"时其实还带着一个条件——

> 状态是"待处理"的可以领;**状态是"已认领"但认领时间已经超过了保质期**的,也算过期,可以重新领。

所以"进程崩了"的最坏情况是:那条反馈先卡在"已认领"一阵子,等保质期一过,自动变回可被认领,
由下一轮 Scheduler 捡起来重新处理。同时 `attempt_count` 会累计;如果一条反馈被反复认领又反复
失败,次数超过上限(`max_attempts`),就不再自动重试,直接转**人工(needs_human)**——避免一条
坏反馈无限循环烧钱。

> 保质期不保证"一定会成功",只保证"不会永远占着茅坑"。任务最终成不成,由后面的流程决定。

## 5. 一次运行(run):这次处理的"档案袋"

Scheduler 认领到反馈后,并不是直接开始跑,而是先建一份"**运行(run)**"档案——数据库里一条
`agent_runs` 记录,给这次处理一个全局唯一编号 `run_id`,并记下:

- 它处理的是哪条反馈、认领牌是什么;
- 用的模型、流水线版本、Prompt 版本(以后能追溯"当时用的是哪套规则");
- 当前进行到哪个阶段、各种预算(调了几次模型、花了多少 token、用了多少容器时间);
- 最终结果(PR 链接 / Issue 链接 / 错误码)。

**一次运行 = 一次完整处理过程的总账本。** 后面所有章节讲的节点、状态、存档,全都挂在这个
`run_id` 下面。

> 人话类比:反馈 = 客户报修的工单;运行 = 维修工接单后开的"派工单"。派工单上记着谁接的、
> 修到哪一步、换了什么件、花了多久。客户最后看到的是派工单上的结果。

认领和运行是两个层面的东西,别混:认领是"数据库里这条反馈归谁",运行是"这次处理的总账本"。
一个对应 `feedback` 表,一个对应 `agent_runs` 表。

## 6. 为什么一次只处理一个任务?

机器跑在 2 核 2G 的小主机上,模型调用、数据库、容器测试已经够忙了。但"单并发"更重要的原因是
**正确性**:

> 每条后端 Bug 的修复都是基于某个固定版本的代码。如果两个任务并行处理、各自改各自的,
> 等到要合并时,它们基于的代码版本可能已经不一样了,会产生冲突。

一次只处理一件,天然避免了这个麻烦:**永远只有一件活在"正在改代码"的状态里**。处理完这件,
Scheduler 再回来领下一件。

## 7. 一张图串起来

```text
用户提交反馈
   │
   ▼
入口 API:校验 → 限流 → 脱敏 → 写库(status=pending)
   │
   ▼
Scheduler 每几秒醒来一次,一次只处理一件:
   │
   ├─ 有没跑完的旧任务? → resume(接着跑,见第 9 章)
   └─ 没有 → 认领一条 pending
        │  认领 = 盖"归我管"的戳:
        │        status: pending → claimed
        │        claim_token: 随机认领牌
        │        claimed_at: 现在 + 保质期到期可重领
        ▼
   建"运行(run)"档案(agent_runs 表,run_id 全局唯一)
        ▼
   把反馈交给外层流水线(Gate)── 下一章从这里开始
```

## 8. 本章出现的关键词速查

| 词 | 人话 | 上一章 / 术语表的对应 |
|---|---|---|
| pending → claimed | 待处理 → 已认领(有人接手了) | 反馈状态字段 |
| claim(认领) | 从队列里捞一件,盖"归我管"的戳 | `feedback.claim_token` |
| claim token(认领牌) | 随机钥匙;之后改这条记录都要出示它 | 防两个进程抢同一任务 |
| lease(保质期) | 认领不是永久;超时自动释放回队列 | 防"进程死了任务卡死" |
| run / run_id(一次运行) | 一次处理的总账本,全局唯一编号 | `agent_runs` 表 |
| attempt_count | 这条反馈第几次被尝试处理 | 超上限就转人工,防无限循环 |
| 入口 / Feedback API | 只做校验、限流、脱敏、写库 | 不处理、不判断 |
