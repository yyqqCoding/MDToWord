# 10 · 三件横切全程的事:权限、沙箱、可观测

> 主线旅程讲完了:安检 → 锁版本 → 复现 → 修复 → 独立终验 → 发 PR 给真人;出错与恢复也讲了。
> 但还有三件事**不属于任何单个节点,而是横切整条流水线**——它们决定了这台机器"为什么敢让 AI
> 自由发挥":
>
> 1. **权限控制(谁说了算)**——全系统"模型只出建议、本地代码拍板"的总开关;
> 2. **隔离沙箱(在哪儿跑)**——所有"真跑代码"发生的地方,物理上够不着主机;
> 3. **可观测(怎么看)**——每次运行的"体检报告",脱敏后给人看。

## 一、权限控制:谁说了算

### 1. 一个贯穿始终的分工

从第一章到现在,你反复看到一个分工,这里把它挑明:

> **模型会犯错、会被骗、会一时糊涂;所以模型永远只"建议"。真正"拍板"的,永远是本地写死的代码。**

"拍板"具体指四件事,都握在固定的几个组件手里,模型碰不到:

| 谁能拍板 | 拍什么板 | 别谁碰 |
|---|---|---|
| **Controller(指挥)** | 一次反馈怎么变成一次运行、怎么组装依赖 | 模型 |
| **Policy(本地守则)** | 安检分类怎么翻译成路由、读写路径授不授权 | 模型 |
| **Validator(校验器)** | 容器结果怎么分类、验证结论成不成立 | 模型 |
| **Publisher(发布器)** | 能不能碰 GitHub、PR/Issue 内容放什么 | 模型、AI 全都没有 GitHub 权限 |

### 2. 权限是怎么"焊死"的:三层锁

"模型不能越权"不是一句口号,是靠三层机制**物理上**保证的:

| 层 | 机制 | 人话 |
|---|---|---|
| **白名单(Patch Policy)** | 一份机器可读的 JSON(`patch_policy.json`),规定能读/能改哪些路径 | AI 想读写任何文件,先过这张表,路径不在表里直接拒绝 |
| **最小工具面** | 内层 AI 只有 8 件工具;Gate 模型干脆 0 工具(`tools=()`) | 连"提议越权"的入口都没有 |
| **最小凭据** | GitHub App 令牌只给固定仓库的 contents/pull_requests/issues 三项写权限,换到的令牌还再核一遍 | 就算代码有 bug,凭据也干不了更多 |

### 3. 白名单那张表长什么样

第四、五章都提过,这里把**真实规则**摆出来(路径都是相对仓库根):

| 用途 | 允许的路径 |
|---|---|
| **可读** | `backend/pyproject.toml`、`AGENTS.md`、`README.md`;`backend/app/` 下所有 `.py`;`backend/tests/` 下所有 `.py` |
| **可写(复现阶段)** | 只有一个文件 `backend/tests/test_feedback_regressions.py` + `backend/tests/fixtures/feedback/` 目录(且只收 `.json/.md/.txt`) |
| **可写(修复阶段)** | 只有 `backend/app/normalizer.py`、`backend/app/pandoc_runner.py` |

外加**规模上限**:单个文件 ≤80KB、工具单次输出 ≤20KB、改动 ≤5 个文件 / 增 ≤300 行 / 删 ≤150
行 / 补丁 ≤200KB。这套规则本身也是**版本化**的(`patch-policy-v3`),运行时从 JSON 加载——AI
改不了,工具也扩不了。

> 白名单反直觉的点再次强调:**能读的面比能改的面宽。** 让 AI 读整片 backend 是为了理解代码,
> 但动手只能落在那几个文件上。想改的文件不在白名单里?宁可转人工,不给越界的刀。

### 4. 可审计性:谁做了什么都有据可查

每个补丁、每个工具调用、每次状态迁移都落存档、记运行状态。补丁以 **Artifact 引用**的形式
存在,大文件进大件仓库,状态里只留指针(第 4 章讲过)。运行状态(AgentState)是**不可变的小卡片**,
从不塞大块内容——这既省 context,也让"谁在哪一步改了什么"永远可以追溯。

## 二、隔离沙箱:所有代码在"够不着主机"的地方跑

### 1. 为什么要单独一个沙箱

这台机器要"真跑代码"——跑 AI 写的测试、跑 AI 打的补丁。而这些代码是**不可信输入**(AI 可能
写错,更可能被恶意 prompt 引导着写坏东西)。如果直接在主机上跑,等于把主机钥匙交给陌生人。
所以所有"真跑",都发生在**和主程序物理隔离的一次性容器**里。

### 2. 容器的"装甲"清单

代码里每个容器都带上这一整套限制(参数全部由本地枚举生成,**不接受模型提供的命令、挂载或
环境变量**):

| 限制 | 值 | 防什么 |
|---|---|---|
| 网络 | `--network=none` | 代码没法偷偷外联、外传数据 |
| 文件系统 | `--read-only` | 主机文件只读,改不动 |
| 内核能力 | `--cap-drop=ALL` + `--security-opt=no-new-privileges` | 容器内拿不到任何特权 |
| 用户 | 非 root(`--user=65532`) | 即使逃逸也只是低权用户 |
| 资源 | 内存 ≤2GB、CPU ≤2、进程数 ≤256 | 恶意代码跑不死主机、烧不穿资源 |
| 临时区 | `/tmp` 512MB(`noexec`) | 可写区域极小且不能执行 |
| 镜像 | **钉死在 sha256 digest** | 今天明天环境完全一致,不可被偷偷换版本 |
| 生命周期 | `--rm` 跑完即毁 | 不留任何残留 |
| 工作区 | 只挂载授权目录;跑完比对工作区改动 | 多动一根手指 = `SECURITY_REJECTED` |

### 3. AI 在沙箱里到底能干什么(不能干什么)

AI 想验证,只能通过**车间工单(SandboxJob)**:工单由本地代码按 `run_id + 阶段 + 轮次` 生成**固定
编号**,写明"用什么 Job 类型、跑哪条 pytest 命令、带哪两个补丁"。AI 能做的**只有"我要验证"**
这一个选择——工单内容它挑不了、命令它给不了、环境它改不了。

> 这是整个安全设计的浓缩:**AI 的自由,是"在锁死的选项里自由",不是"自由地扩大选项"。**

## 三、可观测:每次运行的"体检报告"

### 1. 为什么需要可观测

机器是自动跑的,而且跑一次要花不少模型钱。维护者需要能回答三件事:

1. 这次运行**干了什么**(走了哪些节点、调了多少次模型)?
2. 花了**多少钱**(模型调用、token、容器时长)?
3. **在哪失败的**、为什么?

### 2. 数据去哪:一条脱敏的 Trace

每次运行开始,Controller 就开一条 **Trace 记录**(由 run_id 稳定推导出的 trace_id)。整个运行期间,
每调一次模型、每用一个工具、每跑一次容器,都在这条 Trace 上留下一个**观测节点**。运行结束,
Trace 被推到 **Langfuse**(一个可观测后端),展示在 **Trace Site**(脱敏展示站)网页上。

### 3. 上 Trace 的一切,都先过"脱敏"这一关

这是可观测最要紧的设计:**Trace 上能看到什么,不是"顺手记的",是刻意筛过的。** 所有发往 Trace
的结构化值都过一个统一的脱敏器,它做三件事:

- **按 key 拦截**:名字像 `authorization`、`token`、`password`、`contact` 的字段,整个值替换成
  `[REDACTED]`;
- **按内容打码**:文本里的邮箱 → `[REDACTED_EMAIL]`、手机号 → `[REDACTED_PHONE]`、`Bearer xxx`
  令牌 → 打码、`key=value` 疑似秘密赋值 → 打码;
- **限长截断**:每条文本最多存 300 字符。

这些规则是写死的(`agent/telemetry/masking.py`),并且**用户反馈的联系方式在第 2 章就被隔离了**,
根本走不到这一步。跑测试生成的 JUnit 之类的大内容,上 Trace 前也先经过长度上限和结构摘要。

> 有个细节值得说:为什么连手机号打码的边界都要抠?因为 **SHA-256、git SHA、UUID、镜像 digest**
> 这些标识符里满是大段连续数字,粗心的正则会把它们当成"手机号"误伤——打码打多了,维护者
> 就没法对账了。所以脱敏正则专门排除了十六进制和连字符边界。**脱敏的目标是"该藏的藏,该看的
> 还看得清"。**

### 4. 观测系统自己挂了,怎么办:fail-open

第 9 章讲过,观测是 **fail-open** 的:Langfuse 挂了、Trace 站点挂了,都只记一行日志,**绝不
阻断业务收口**。理由很简单——"看不了病"不能变成"连病都治不了"。

### 5. 运行结束,主动"叮"一声站点

老设计里,Trace 站点靠**每日定时回填**,刚跑完的运行最长要等 24 小时才看得到明细。现在改成了
**运行一进终态,Agent 主动推一个 webhook 通知站点**。这个推送有严格边界:

- **只推 run_id,不推内容**——站点收到信号后自己去 Langfuse 取 Trace,投影逻辑只存在于站点一侧;
- **at-most-once**:丢了就丢了,站点按需补抓,不影响修复;
- 推送前先 flush Langfuse——因为 Langfuse 是后台批量上报,不 flush 就通知,站点多半拿到半截树。

### 6. 可观测 + 不可信原则的相遇

最后把这一章三件事串起来看:为什么可观测也得讲"不可信"?因为**连观测数据本身也是不可信输入**
——测试日志可能是 AI 生成的、可能夹带东西。所以 Trace 上的内容要脱敏、要限长、要结构摘要;
展示站展示的只是**脱敏投影**,不是原始数据。**这台机器处理一切外部数据的姿势,从头到尾是同一个。**

## 附:整份指南的"全景图"

把十章连起来,一份"正经后端 Bug"反馈的完整旅程是:

```text
用户提交反馈
   │
   ▼ ① 入口:校验 → 限流 → 脱敏 → 存库(pending)
   ▼ ② Scheduler 认领(claim)+ 建运行(run);一次只领一件
   ▼ ③ 安检 Gate:分类员填表 + 本地守则拍板 → 六条出口之一
   │      └─ 正经后端 Bug → ④ 锁版本(快照 + base_sha + 白名单)
   │                              ▼
   │                    ⑤ Repair Agent:转换探针 → 复现 → 修复(ReAct 循环)
   │                              ▼
   │                    ⑥ 收场分流:成功→validating;复现不出/失败/求援→各自终态
   │                              ▼
   │                    ⑦ 独立终验:三个全新容器(基线/目标/全量 + DOCX)
   │                              ▼
   │                    ⑧ 发布器:唯一碰 GitHub 的手 → PR(或 Issue)给真人
   ▼
横切全程:权限控制(本地代码拍板) / 隔离沙箱(够不着主机) / 可观测(脱敏 Trace)
         出错与恢复(checkpoint 续跑 / 失败分类 / 预算刹车)
```

机器能自动做的,到这里全部做完了。剩下的那一步——打开 PR、review 代码、合并、部署,再拿用户
那段原始 Markdown 在真实的 Word 里肉眼确认——永远属于**人**。
