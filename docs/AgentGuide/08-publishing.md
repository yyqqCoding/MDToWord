# 08 · 发布边界与幂等设计

本章说明通过独立验证的候选修复如何成为可审核的代码合并请求（PR），以及功能需求或扩展
问题如何成为脱敏问题或需求单（Issue）。发布器（Publisher）是全系统唯一执行 GitHub 外部
写入的受信组件；模型、内层工具和其他外层节点都不能直接创建协作对象。

本文首次引入的术语如下：代码合并请求（Pull Request，简称 PR）是等待维护者审核的代码变更；
问题或需求单（Issue）是 GitHub 上用于协作的条目；反馈分类器（Gate）负责生成分类结果；
本地策略（Policy）负责校验分类结果和发布条件；主分支（main）是补丁基于的仓库分支；
GitHub App（受限仓库应用身份）用于执行
受控仓库操作；流程状态（Graph State）保存运行进度；制品存储（Artifact）保存快照、补丁和验证结果；
端到端追踪（Trace）记录一次运行的观测关系；结构化编辑（Edit）是模型提交的候选改动；
幂等标记（marker）是嵌入正文、用于识别已完成副作用的稳定标识；基础版本过期（stale_base）
表示补丁基于的 `main` 已经发生变化。

## 1. 发布器的职责边界

自动化链路的终点是“产生可审核的 PR 或 Issue”，不是合并、部署或替用户确认最终 Word 效果。
发布器只负责以下动作：

| 分支 | 输入 | 输出 |
|---|---|---|
| PR 发布 | 已通过独立验证的补丁和结构化证据 | 固定分支、提交和 PR |
| Issue 发布 | Gate 生成并经 Policy 校验的脱敏草稿 | 脱敏 Issue |

发布器不负责重新推理问题、不修改补丁、不运行测试，也不解释模型文字。这样可以将 GitHub
外部副作用集中在一个边界内，便于权限审查、重复检测和失败恢复。

## 2. GitHub 权限最小化

发布器使用 GitHub App 的短期安装令牌。当前权限遵循最小化原则：

- 仅针对固定仓库；
- 只授予创建所需的 `contents`（仓库内容）、`pull_requests`（PR）和 `issues`（Issue）
  权限；
- 不提供合并、Actions、Secrets、部署或其他仓库管理能力；
- 令牌按需获取，只存在于受信进程内，不写入文件、日志、Graph State、Artifact、Trace、
  PR 或 Issue；
- 获取令牌后再次校验仓库和权限集合，发现超出预期就拒绝发布。

PR Publisher（PR 发布适配器）只能创建指定仓库的分支、提交和 PR；Issue Publisher（Issue
发布适配器）只能创建 Issue。即使某个发布调用发生逻辑错误，凭据也不会提供超出当前分支
所需的能力。

## 3. PR 发布前的证据检查

只有 `ValidationResult`（独立验证结果凭据）为 `passed=true` 时，才允许创建 PR。发布器在
调用 GitHub 前重新检查：

1. `base_sha` 与源码快照哈希仍然匹配；
2. `validated_patch`（已验证补丁）的 SHA-256 与验证结果一致；
3. 补丁改动文件清单与验证结果一致，并且再次通过补丁策略（Patch Policy）；
4. PR 内容只来源于结构化验证证据和运行元数据；
5. 外部仓库中不存在同一反馈和同一补丁已经产生的发布副作用。

发布器重新物化补丁，而不是直接使用模型提交的原始 Edit。这样可以防止 Artifact 被替换，
也防止“验证的是 A，发出去的是 B”。

## 4. PR 的创建流程

通过发布前检查后，Publisher 依次完成：

```text
读取 validated_patch 和 ValidationResult
  -> 在固定源码快照上重新物化并对账
  -> 根据 feedback_id 和类别计算确定性分支名
  -> 使用 Git 数据 API（Git Data API）创建 Tree、Commit 和分支引用
  -> 生成只含结构化证据的 PR 正文
  -> 扫描敏感内容
  -> 查重后创建或复用 PR
```

分支名、提交标题和发布标识具有确定性，例如分支名包含反馈短 ID 和 Gate 类别。PR 正文包含：

- 本次自动修复的类别和反馈短标识；
- 基线失败、目标通过、全量测试和 DOCX 检查结果；
- 改动文件、风险级别、流程/策略/提示词（Prompt）版本和用量；
- `base_sha`、已验证补丁哈希和 Trace 链接。

正文结构上不提供用户原始描述、Markdown 或联系方式字段；生成后仍会执行邮箱、令牌、秘密赋值
和提示词注入模式扫描，发现异常就拒绝发布。敏感扫描是最后一道检查，不替代发布请求契约和
权限控制。

## 5. 重复发布与幂等

发布请求可能在 GitHub 已成功写入后丢失响应。如果简单重试，会产生重复分支、提交或 PR。系统
在 PR 正文末尾写入幂等标记（marker），内容绑定反馈 ID 和已验证补丁哈希：

```html
<!-- mdtoword-agent feedback=... patch=... -->
```

重试时先按反馈、分支和 marker 查询现有结果：

```text
查找已有副作用
  ├─ 找到相同 marker -> 复用已有 PR
  ├─ 找到同一分支但内容冲突 -> 作为发布冲突终止
  └─ 未找到 -> 创建一次新的发布对象
```

Issue 使用独立 marker，将运行引用和内容指纹绑定到正文。稳定的 `operation_id`、分支名、marker
和补丁哈希共同构成幂等依据；重试只能复用相同受信输入，不能重新生成一个语义相近但标识不同
的发布对象。

## 6. stale_base：发布前主分支已经变化

源码快照固定的是修复开始时的 `base_sha`。发布前如果当前 `main` 的提交不同，发布器返回
`stale_base`，不创建基于旧版本的 PR，也不自动 rebase（变基）旧补丁。

处理规则如下：

| 连续发生次数 | 处理 | 原因 |
|---:|---|---|
| 第一次 | 将反馈转为 `stale_base`，再排回 `pending`，重新锁定版本、复现、修复和验证 | 新版本可能已经修复问题或改变调用关系 |
| 第二次 | 转为 `needs_human`，不再自动排队 | 防止主分支频繁变化造成无限重跑 |

`stale_base` 不是短传输重试。它改变了验证前提，必须重新建立完整证据链；自动重排最多一次，
由 `stale_requeue_count` 记录次数。

## 7. Issue 发布分支

功能需求或扩展问题由 Gate 生成脱敏标题和摘要，经 Policy 校验后进入 Issue 发布。Issue 输入
结构只包含：

- 脱敏标题、摘要和分类字段；
- 运行版本、模型用量和可选 Trace URL；
- 反馈内容指纹和运行引用，用于幂等查重。

Issue 不携带代码补丁、源码、原始反馈、联系方式或完整日志。发布前对标题和正文再次执行敏感
模式及指令模式扫描；失败则转人工或发布失败，不通过解释草稿内容来放宽边界。

## 8. 发布完成后的人工边界

PR 创建成功后，反馈进入 `pr_opened`；Issue 创建成功后，反馈进入 `issue_opened`，运行记录
保存对应 URL。自动化到此结束：

```text
Publisher 创建 PR/Issue
  -> 维护者 review（代码审核）
  -> 维护者 merge（合并）
  -> 维护者部署
  -> 在真实 Word 环境确认最终视觉效果
```

系统不提供自动合并、部署或人工视觉判断权限。这样既保留自动化的重复劳动收益，也将最终代码
责任和用户可见效果确认保留在维护者手中。

## 9. 发布失败与恢复

临时网络失败只在幂等发布操作上进行有界重试。若发布已经失败但验证证据仍然有效，维护者可以
显式恢复原 `run_id`，只重启发布检查点，不重新执行模型、Sandbox 或最终验证。若失败原因是
`stale_base`，按本章规则重新排队一次；认证、权限、配置和发布冲突不通过重复请求绕过。

具体失败分类和恢复边界见 [09 · 失败处理与恢复](09-failures-and-recovery.md)。
