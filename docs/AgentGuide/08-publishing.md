# 08 · 发布:验证通过,变成一条 PR / Issue

> 上一章([07](07-independent-final-validation.md))的独立终验通过了,反馈进了 publishing。
> 这一章讲整台机器**唯一能碰 GitHub** 的环节——**发布器(Publisher)**。
>
> 前七章机器都在"内部"干活:读库、分类、锁版本、跑车间。到了这一章,机器第一次要跟外部世界
> (GitHub)打交道——把一条验证过的修复变成 PR、或把一条功能建议变成 Issue,交到维护者(真人)
> 手里。这也意味着本章必须回答一个前面没出现过的问题:**怎么安全地、不重不漏地把东西发出去。**

## 1. 一句话:发布器是唯一能碰 GitHub 的手

从第一章到现在,你可能注意到一个反复出现的说法:"模型没有 GitHub 权限""AI 发不了 PR"。这不只是
说说——在代码层面,整条流水线里**只有发布器这一个环节拿着 GitHub App 的令牌**,其他任何节点、
任何 AI、任何工具都碰不到 GitHub。

这个 GitHub App 的权限还刻意做到**最小**:

- 只能访问**固定的那个仓库**;
- 令牌上写死只允许 `contents`(写文件)、`pull_requests`(开 PR)、`issues`(开 Issue)三件事的写权限;
- 令牌按需换取、短期有效、只活在进程内,**不落盘、不进日志**;
- 每次换到的令牌,代码还会**再核一遍权限**:发现多了任何一项,直接报错拒绝,不干活。

一句话:**想碰 GitHub,只有发布器这一条路;连发布器自己,也被限制得死死的。**

## 2. 发 PR:机器把"完整修复方案 + 证据"端到人面前

当独立终验通过、反馈进入 publishing,发布器会创建一个 PR。它做的事很明确:**把这次验证过的补丁,
变成一个真实的 GitHub 分支 + 提交 + PR,交给人 review。**

具体是这么一步步来的:

1. **重新物化补丁**:发布前,代码会从存档里把"已验证补丁"重新铺到锁死的那份源码上,并核对它
   的哈希和改动文件清单——**跟终验记录的必须一字不差**。这是为了防止存档被人偷偷替换、或文件
   集合漂移("验证的是 A,发出去的是 B"这种事绝不允许)。
2. **算出一个固定分支名**:分支名由 feedback id 和类别**确定性地**算出来
   (比如 `agent/feedback-ab12cd34-formula_parsing`),不是随机数。
3. **用 Git Data API 提交**:不借用本地 git 命令行,而是直接调 GitHub 的底层 API,把改动文件、
   提交、分支引用一步步建出来,每个中间结果都校验格式。
4. **开 PR**,正文里写清四样东西:
   - **干的是什么**:哪条 feedback、哪个类别;
   - **四条验证证据**:基线仍失败 / 目标测试通过 / 全量测试干净 / DOCX 检查;
   - **改了哪些文件** + 风险级别 + 用了哪些模型和 prompt 版本 + 花了多少钱;
   - **可追溯锚点**:base_sha、已验证补丁哈希、Trace 链接。

> 注意 PR 正文的**唯一内容来源**是上一章那个结构化验证结论(ValidationResult)。代码里有一句写死
> 的注释:"只使用结构化验证摘要生成正文,**绝不拼接用户描述或 Markdown**。"用户的原始反馈、原文、
> 联系方式——在结构上就**进不了**发布请求。正文最后还会再过一遍**敏感模式扫描**(邮箱、令牌、
> 提示词注入字样),发现任何可疑就拒绝发布。宁可不发,不泄露。

### 2.1 怎么保证"不重复发":一个看不见的 marker

机器可能因为网络抖动、进程崩溃而**重试**。如果每次重试都新建一个 PR,同一个 Bug 就会冒出好几条
一样的 PR。怎么防?

发布器在每个 PR 正文末尾藏了一行**看不见的 HTML 注释(marker)**,里面写着 feedback id 和已验证
补丁的哈希:

```html
<!-- mdtoword-agent feedback=… patch=… -->
```

发布前,它先拿这个 marker 去 GitHub 上搜:**已经有一模一样的 PR 了?** 有就**复用**它,不新建。
这个"先查再建、查到了就复用"的流程,加上"固定分支名 + marker"组成的幂等键,保证了一次重试
**不会**产生重复 PR——即使"PR 其实已经建成功、只是响应丢了"这种最尴尬的情况,重试也能靠
marker 找回那条已存在的 PR,而不是再建一条。

## 3. 突发情况:准备发 PR 时,发现 main 已经变了(stale_base)

这是发布阶段最微妙的时刻。回顾一下时间线:

- 机器在**第 4 章**把 main 当时的代码锁成了 `base_sha`,所有测试都在这份固定副本上做;
- 验证也通过了,补丁在这份副本上**确实有效**;
- 但是——准备发 PR 的那一刻,机器回头一看:**main 分支已经前进了**,已经不是我们测的那版了。

这个状态叫 **stale_base(main 变了)**。为什么不能直接发?因为我们的补丁是**基于旧版 main** 打的。
直接开 PR,会跟最新的 main 产生冲突;更糟的是,万一 main 前进时恰好改了同一段代码,我们的修复
可能已经过时甚至有害——发出去就是一份**没在新版上验证过的**改动。

所以发布器会这样处理:

| stale_base 发生次数 | 动作 | 为什么 |
|---|---|---|
| **第 1 次** | 把反馈**重新排回待处理队列**,让整条流水线**从头再来一遍**:重新锁新 main、重新复现、重新修、重新验 | 新版 main 可能已经自己好了,也可能只是代码挪了位置——重跑一遍是唯一诚实的做法 |
| **第 2 次(连续)** | **不再自动重试**,转人工 | 连撞两次说明 main 变得太频繁,自动重试只会无限循环烧钱,交给真人判断 |

> 这个"只自动重排一次"的决策藏在 `stale_requeue_count` 这个计数器里。它的哲学和前面完全一致:
> **机器可以自动重试,但绝不无限重试**——撞到某个上限,就诚实地说"我搞不定,请人来看"。

## 4. 分支剧情:发 Issue(功能建议 / 前端问题)

还记得第 3 章安检的 Issue 支路吗?如果用户提的是"想要新功能"或"前端扩展坏了",不进自动修复链,
而是走发布器的**另一个出口**:发一条 GitHub Issue,交给维护者排期。

发 Issue 和发 PR 有几处关键差异:

| | 发 PR | 发 Issue |
|---|---|---|
| 内容来源 | 验证证据(ValidationResult) | **安检时拟好的脱敏摘要**(第 3 章) |
| 带什么 | 补丁文件 | 不带任何代码,只有文字 |
| 标签 | — | bug / enhancement |
| 幂等 marker | `mdtoword-agent … patch=…` | `mdtoword-agent-issue … run-ref=… fingerprint=…` |

Issue 正文同样**只放脱敏后的摘要和分类字段**,最后明确声明:"This issue was generated from a
sanitized user suggestion. It does not contain the original submission."(本 issue 由脱敏后的用户
建议生成,不含原始提交。)最后同样过一遍敏感模式 + 提示词注入扫描,然后才发出去。

## 5. PR / Issue 发出之后:机器收工,真人拍板

发布完成后,反馈状态变成 **pr_opened**(PR 已开)或 **issue_opened**(Issue 已开),运行记录写进
PR/Issue 链接,整次运行收工。

**请注意:PR 永远不会被自动合并。** 这是整套系统最重要的一条边界——机器能做的是:把"一个 Bug
的完整修复方案 + 四条独立证据 + 改了什么 + 花了多少"端到维护者面前。真正 merge、部署、上线,
由维护者(真人)来做;最后还要拿用户那段原始 Markdown 在**真实的 Word** 里肉眼确认一遍效果。
自动化的终点,永远是人的起点。

## 6. 这一章的流程图

```text
终验通过(反馈:validated → publishing)
   │
   ▼
publish_pull_request 节点(发布器,唯一能碰 GitHub 的环节)
   │  1 重新物化补丁 + 核对哈希/文件清单(防偷换)
   │  2 算固定分支名 → 用 Git Data API 建提交和分支
   │  3 拿 marker 先查:已有一样的 PR?→ 复用,不新建(幂等)
   │  4 生成 PR 正文:只从验证证据拼,绝不含用户原文
   │  5 敏感模式扫描(邮箱/令牌/注入字样) → 不过就不发
   │
   ├─ 一切顺利 → 反馈 pr_opened,收工
   │
   └─ main 已前进(stale_base)
        │  stale_requeue_count == 0 → 反馈重新排回待处理,整条重跑一遍
        └ 已连续撞 2 次 → 转人工,不再自动重试
```

## 7. 这一章出现的关键词速查

| 词 | 人话 | 对应代码/位置 |
|---|---|---|
| 发布器(Publisher) | 全系统唯一能碰 GitHub 的环节(PR + Issue) | `agent/publishing/github.py` |
| GitHub App 最小权限 | 只能写固定仓库的 contents/pull_requests/issues,换到的令牌还再核一遍 | `GitHubAppTokenProvider` |
| marker | 藏在 PR/Issue 正文里的 HTML 注释,作幂等键 | `_publication_marker` / `_issue_marker` |
| 敏感模式扫描 | 发布前最后一道边界:邮箱、Bearer、Secret、注入字样 | `_SENSITIVE_PATTERNS` |
| stale_base | 发 PR 时发现 main 已前进,补丁不是基于最新版打的 | 第 4 章 base_sha 的对照 |
| stale_requeue_count | main 漂移自动重排次数,连续 2 次就转人工 | `finish_publication` 节点 |
| pr_opened / issue_opened | 发布完成后的反馈终态 | 反馈状态 |
| 永不自动合并 | PR 只交给人 review/merge,机器无权合并 | 全系统设计边界 |

到这里,一条"正经后端 Bug"反馈的完整旅程就讲完了:**安检 → 锁版本 → 复现 → 修复 → 独立终验 →
发 PR 给真人**。但机器能可靠地走完这段旅程,靠的是藏在底下的健壮性设计——下一章讲**出错与恢复**。
