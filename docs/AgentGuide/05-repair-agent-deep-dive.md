# 05 · 修复代理工具循环设计（Repair Agent）

本章说明自动修复链中唯一允许模型进行连续探索的部分。修复代理（Repair Agent）运行在内层
工具循环中，负责搜索源码、形成测试或修复候选并观察执行结果；外层流程、权限、状态、预算、
验证和发布仍由受信代码控制。

本文首次引入的术语如下：观察—行动循环（ReAct）表示模型根据工具结果继续选择下一项动作；
`create_agent` 是承载该循环的组件构建方式；阶段（phase）表示 `reproducing`（复现）或
`repairing`（修复）；控制器（Controller）负责启动探针和外层流程；隔离执行环境（Sandbox）是
执行固定测试任务的一次性容器；受信执行任务（Job）是由本地代码固定命令、补丁和资源限制的
结构化任务。

## 1. 设计目标：保留探索，限制能力

对于未知后端缺陷，完全固定模型步骤会导致两个问题：

- 无法预先知道需要搜索的符号和调用链；
- 每一种反馈都需要额外编写一条固定流程。

因此，系统只把“当前阶段下一步做什么”交给模型选择，其他事项保持固定：

| 由模型探索 | 由本地代码决定 |
|---|---|
| 读取哪个已授权文件、搜索什么关键词 | 当前阶段、工具集合和文件白名单 |
| 是否根据结果重新编辑候选 | 补丁结构、规模、路径和状态前置条件 |
| 提交哪个候选测试或修复编辑 | Sandbox 命令、镜像、挂载和资源限制 |
| 根据结构化结果决定下一次观察 | 预算、完成条件、独立验证和发布条件 |

模型的候选动作不直接写入宿主机，也不能直接改变业务状态。工具函数会将候选动作转换为受信
结果，并把结果写入内层检查点（checkpoint，用于中断恢复的持久化记录）。

## 2. 转换探针（conversion probe）：先确定复现入口

修复代理启动前，Controller 先执行转换探针（conversion probe，即只判断当前 Markdown 是否
在后端转换阶段直接抛出转换错误的确定性检查）。探针不调用模型，也不判断用户主观的视觉
偏好；它只为后续复现选择正确的证据路径。

| 探针结果 | Controller 行为 | Agent 的下一步 |
|---|---|---|
| 后端转换抛出错误 | 根据安全错误摘要生成固定转换回归测试 | 直接验证固定测试，再进入修复阶段 |
| 转换成功 | 不预设用户的语义断言 | 设计语义回归测试，并先证明基线失败 |
| 无法形成稳定测试 | 不生成未经证明的修复任务 | 结束为 `cannot_reproduce` 或 `needs_human` |

这种分流避免将“程序抛错”和“输出结果不符合预期”混为同一类问题。前者可以使用固定的
异常断言，后者必须将反馈转换为受信、可重复的语义断言。探针也不替代最终 Word 文档结构验证器
（DOCX Validator）；最终结构检查仍属于独立验证阶段。

## 3. 两个阶段与状态前置条件

内层循环只允许按以下顺序推进：

```text
reproducing
  -> 提交 test patch
  -> 运行基线 Sandbox
  -> 结果确认 REPRODUCED
repairing
  -> 提交 fix patch
  -> 运行目标测试 Sandbox
  -> 结果确认 TARGET_PASSED
```

### 3.1 复现阶段

复现阶段只能修改回归测试文件和反馈固件。测试补丁应用到固定 `base_sha` 后，必须在未应用
修复补丁的基线环境中按预期失败。当前一轮结果需要由受信 JUnit（测试报告格式）摘要确认，
模型不能通过普通文字宣称“测试失败”。

复现最多两轮。结果可能是：

| 结果 | 含义 | 外层处理 |
|---|---|---|
| `REPRODUCED` | 目标测试按预期失败，问题获得基线证据 | 进入修复阶段 |
| `NOT_REPRODUCED` | 测试未按预期失败 | 允许在剩余轮次调整，否则无法复现 |
| `INVALID_TEST` | 测试或断言不符合契约 | 允许修正，不能直接修复代码 |
| `BASELINE_REGRESSION` | 基线基础检查异常 | 视为复现证据无效 |
| `SECURITY_REJECTED` | 工作区出现未授权改动 | 立即终止 |

### 3.2 修复阶段

修复阶段必须已经拥有受信的 `REPRODUCED` 结果，之后才能修改
`normalizer.py` 或 `pandoc_runner.py`。每轮提交最小修复补丁，并使用固定目标测试验证。
修复最多两轮；目标测试通过后只能调用完成工具，不能继续追加任意改动。

修复阶段的通过只表示目标测试在当前 Agent 任务中通过，不能跳过 [07 · 独立验证与证据链](07-independent-final-validation.md)。

## 4. 工具集合与能力边界

内层共有八个业务工具，另有一个用于维护任务清单的规划工具：

| 工具 | 作用 | 开放阶段 |
|---|---|---|
| `search_source` | 在白名单源码中进行有界搜索 | 复现、修复 |
| `read_source_file` | 按路径和行范围读取白名单文件 | 复现、修复 |
| `submit_test_edits` | 生成并校验测试补丁 | 复现 |
| `run_sandbox` | 执行当前受信 Sandbox Job | 存在待验证补丁时 |
| `submit_fix_edits` | 生成并校验修复补丁 | 修复 |
| `complete_reproduction` | 确认基线已按预期失败 | 复现 |
| `complete_repair` | 确认目标测试已通过 | 修复 |
| `report_blocked` | 报告无法继续或需要人工 | 任意内层阶段 |
| `write_todos` | 维护结构化 Todo（任务清单） | 任意内层阶段 |

工具集合中明确没有命令执行工具（Shell）、通用文件系统工具（Filesystem）、网络、
GitHub、数据库或凭据工具。模型不能提交命令字符串、工作目录、环境变量、网络地址或自定义
自定义任务标识（Job ID）。

## 5. 工具可见性与二次校验

工具权限由两个层次共同保证：

1. 阶段策略根据 `phase` 隐藏不适用工具，例如复现阶段不开放修复提交；
2. 子状态策略根据当前是否存在待验证补丁、是否已有受信结果进一步收窄工具。

典型状态如下：

```text
没有补丁       -> 可读取源码、提交当前阶段补丁
补丁待验证     -> 只开放 run_sandbox
Sandbox 通过   -> 只开放对应完成工具
完成或阻塞     -> 内层循环结束
```

工具即使没有展示给模型，执行函数仍会再次检查阶段、路径、补丁哈希、前置产物、预算和
checkpoint。Middleware（中间件，即包裹模型和工具调用的本地控制逻辑）不是唯一安全边界。
缺少前置产物时返回脱敏的 `ToolMessage`（工具结果消息）和 `required_action`；越权路径或
未登记工具则直接安全拒绝。

## 6. ReAct 循环中的补丁和 Sandbox

典型循环为：

```text
搜索/读取源码
  -> 提交 test.patch 或 fix.patch
  -> 调用 run_sandbox
  -> 读取 JUnit 和有限执行摘要
  -> 继续编辑、完成阶段或报告阻塞
```

`run_sandbox` 不接受模型命令。Controller 根据 `run_id`、阶段、轮次、`base_sha`、补丁引用
和目标测试选择器生成 Job；执行工作进程（Worker）将 Job 映射为固定 `argv`（命令参数数组）、固定镜像和
资源限制。模型能够选择“请求验证”，但不能选择验证命令、容器权限或工作目录。

Job 的执行结果至少包含执行状态、退出码、JUnit 摘要、目标测试是否收集、目标结果、超时
信息和工作区改动哈希。完整日志只保存在受控制品存储（Artifact），返回给模型的结果必须有界并脱敏。

同一个 Job 使用稳定的 `job_id`、请求指纹和幂等键。临时传输失败的重试复用同一个任务，不
重复执行已经保存结果的容器；Worker 仍按单并发执行 Sandbox。

## 7. Middleware 的职责

生产 Repair Agent 注册以下本地控制逻辑：

| Middleware | 设计职责 |
|---|---|
| TodoListMiddleware | 管理结构化任务清单 |
| RepairSummarizationMiddleware | 上下文达到有效窗口 65% 时压缩历史消息，保留最近 20% |
| HardContextLimitMiddleware | 压缩后仍达到 85% 时停止，避免模型基于截断信息猜测 |
| ModelResilienceMiddleware | 模型临时失败按主模型、主模型、备用模型执行三次总尝试 |
| PhaseToolPolicyMiddleware | 按阶段和子状态收窄工具并检查调用 |
| ParallelToolPolicyMiddleware | 拒绝副作用冲突的同批工具调用 |
| RecordingToolRetryMiddleware | 只为 Sandbox 临时传输失败提供三次总尝试 |
| ToolErrorMiddleware | 将参数或前置条件错误转换为脱敏 ToolMessage |
| ModelCallLimitMiddleware / ToolCallLimitMiddleware | 执行持久化模型和工具总预算 |
| CompletionGuardMiddleware | 禁止普通文本绕过完成工具 |

只读搜索和读取可以并行；补丁写入、Sandbox 和完成工具不能与其他动作并行。并行规则只用于
降低只读查询延迟，不扩大生产 Worker 的执行并发。

## 8. 预算与停止条件

默认运行预算为：

| 预算 | 默认上限 | 超限处理 |
|---|---:|---|
| 复现轮数 | 2 轮 | 结束复现并记录无法继续 |
| 修复轮数 | 2 轮 | 结束修复并记录失败 |
| 模型调用 | 50 次 | 进入 `budget_exhausted` |
| 工具调用 | 30 次 | 进入 `budget_exhausted` |
| Sandbox 总时长 | 900 秒 | 进入 `budget_exhausted` |

单次模型请求默认超时 180 秒，可配置范围为 30～300 秒；这只是单次请求上限，不是整个运行
的总预算。预算计数持久化在内层状态，显式恢复时不能重置历史计数。

内层在以下情况结束：完成工具通过受信结果、`report_blocked` 报告稳定阻塞、模型/工具/上下文
预算耗尽，或发生安全、权限、认证和永久配置错误。内层结束后，外层仍必须执行独立终验和
发布前检查。

## 9. 设计取舍

| 设计 | 解决的问题 | 代价 |
|---|---|---|
| 一个有限 ReAct Agent | 适应未知调用链和测试设计 | 需要维护阶段状态、工具策略和恢复逻辑 |
| 工具而非 Shell | 保留探索能力，拒绝任意命令和网络 | 临时诊断能力受限 |
| 探针区分崩溃和语义问题 | 让异常类问题使用确定性复现证据 | 需要维护两类复现入口 |
| 先复现再修复 | 防止根据用户描述盲目改代码 | 复现困难的问题会转人工 |
| 本地完成守卫 | 防止模型自然语言伪造成功 | 需要保存并校验每次 Sandbox 结果 |
