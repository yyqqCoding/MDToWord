# 07 · 独立验证与证据链设计

本章说明候选修复为什么不能直接进入发布，以及 `validate_final`（独立最终验证节点）如何在
全新执行环境中重新构造证据。独立验证的目标不是重复模型操作，而是让最终结论只由受信
测试结果、补丁完整性和 DOCX 结构检查计算得到。

本文首次引入的术语如下：JUnit（测试结果报告格式）用于提供结构化测试摘要；DOCX（Word 文档
格式）检查用于验证导出文档的受信结构；ValidationResult（验证结果）是由 Controller（控制器）
计算的最终验证凭据；目标测试（target test）是本次反馈新增并用于证明问题已修复的回归测试；
修复代理（Repair Agent）是提交候选测试和修复的内层工具循环；代码合并请求（PR）是验证通过
后交给维护者审核的发布对象。

## 1. 独立验证要防止什么

内层 Repair Agent 只能证明“它在当前循环中提交的候选补丁，使当前目标测试通过”。如果直接
相信这一结果，仍存在以下风险：

1. 测试断言过弱，基线本来就不会失败；
2. 修复只覆盖目标样例，破坏其他后端行为；
3. 测试被跳过或没有真正收集到；
4. 执行环境中的改动超出授权补丁；
5. DOCX 输出结构与测试声明不一致。

因此，最终验证必须满足“基线失败、目标通过、全量无回归、DOCX 检查通过”四类证据，且不
复用模型刚刚使用过的容器。

## 2. 三个全新 Sandbox Job

隔离执行环境（Sandbox）的执行工作进程（Worker）根据固定受信执行任务（Job）类型创建三个一次性容器。三项
任务都绑定同一个 `base_sha`（基础提交标识）和源码快照，差异只在于携带的补丁和执行目标：

| Job 类型 | 补丁 | 执行内容 | 必须满足 |
|---|---|---|---|
| `reproduce_target` | 仅测试补丁 | 目标测试 | 基线仍按预期失败 |
| `validate_target` | 测试补丁 + 修复补丁 | 目标测试 | 目标测试通过 |
| `validate_full` | 测试补丁 + 修复补丁 | 后端全量测试和 DOCX 检查 | 无失败、无错误，目标测试被收集且通过 |

Job 的命令参数、测试选择器、镜像、资源限制和 `job_id`（任务标识）由本地代码生成，模型
不能修改。每个容器执行结束后返回有界的结构化结果，包括 JUnit 摘要、超时状态、目标测试
结果和工作区改动哈希。

### 2.1 基线任务

基线容器只应用测试补丁，不应用修复补丁。它必须产生与预期失败类型匹配的结果：

- 语义测试通常预期断言失败；
- 固定转换测试预期出现转换错误；
- 测试必须被收集并实际执行；
- 容器工作区只能包含授权的测试补丁。

如果基线没有失败，不能证明测试有效，最终验证直接失败。

### 2.2 目标任务

目标容器同时应用测试补丁和修复补丁，只运行目标测试。它必须得到完成状态、有效 JUnit 摘要，
目标测试被收集且通过，并且没有超时或其他测试错误。

### 2.3 全量任务

全量容器使用同一组补丁运行后端完整测试集。除了失败数和错误数必须为零，还要满足：

- 被跳过的测试数量不能高于基线统计；
- 目标测试必须被收集并通过；
- DOCX 检查必须返回通过；
- 执行后的工作区差异必须等于授权补丁产生的差异。

目标测试在全量任务中再次确认，是为了避免通过改变收集规则或跳过配置伪造“全量通过”。

## 3. DOCX 结构检查

对于公式、表格、图形和其他文档结构问题，测试会调用受信的 DOCX Validator（Word 结构验证器）。
模型只能选择已经登记的断言类型和有限参数，不能提交任意 XPath、Python 回调或动态命令。

DOCX 检查属于 `validate_full` 的受信结果，不是模型自述，也不是单独授权的一条发布路径。它
验证的是可确定的文档结构，例如必要部件存在、公式或图形数量达到最低值、XML 可以解析等。
主观视觉偏好如果无法转化为稳定断言，不能进入自动修复链。

## 4. ValidationResult 的计算规则

Controller 根据三个 Job 的结果计算 `ValidationResult`。模型不能提供或覆盖 `passed` 字段：

```text
passed
  = baseline.executed
  ∧ baseline.expected_failure_observed
  ∧ target.passed
  ∧ full.passed
  ∧ docx.passed
```

四类条件缺一不可。失败原因按固定顺序生成，保证相同输入得到稳定解释：

| 优先级 | `failure_code` | 判定 |
|---:|---|---|
| 1 | `baseline_reproduction_failed` | 基线没有观察到预期失败 |
| 2 | `target_validation_failed` 或目标结果错误 | 修复后目标测试未通过或结果不可信 |
| 3 | `skipped_tests_increased` | 全量跳过数高于基线 |
| 4 | `full_validation_failed` | 全量测试存在失败、错误、超时或其他不合格结果 |
| 5 | `docx_validation_failed` | 受信 DOCX 检查未通过 |

`ValidationResult` 自身还要通过一致性校验：`passed` 必须与全部子结果的逻辑与一致；通过时
不能携带失败原因；失败时必须携带稳定的 `failure_code`。这样可以避免“子结果失败但总结果
被写成通过”的状态污染。

## 5. 补丁和工作区完整性

测试结果通过后，还需要对最终发布内容做静态对账：

1. 将测试补丁和修复补丁组合为 `validated_patch`（已验证补丁）；
2. 重新计算已验证补丁的 SHA-256 和修改文件清单；
3. 检查三个容器的工作区差异只包含授权修改；
4. 将补丁引用、哈希、`base_sha` 和快照哈希写入验证结果。

发布器只接受这份验证结果及其绑定的补丁，不接受模型原始编辑或单次容器日志。任何文件集合、
哈希或授权差异不一致，都不能进入 PR 发布。

## 6. 通过和失败的后续状态

外层 `finish_validation`（验证收场节点）读取受信 `ValidationResult`：

| 结果 | 反馈状态 | 运行后续 |
|---|---|---|
| `passed=true` | `validated`，随后进入 `publishing` | 交给 PR Publisher（PR 发布器） |
| `passed=false` | `failed` | 保存验证报告，结束自动修复 |
| 结果不一致或安全拒绝 | `failed` 或 `security_rejected` | 按失败类型终止，不由模型解释放行 |

验证失败不会自动修改测试或修复补丁。若要再次尝试，应由新的运行或维护者明确触发，避免在
同一证据链上悄悄替换验证对象。

## 7. 设计取舍

| 设计 | 解决的问题 | 代价 |
|---|---|---|
| 三个全新容器 | 隔离内层环境和补丁组合，避免结果互相污染 | 执行时间和资源成本增加 |
| 基线/目标/全量三种视角 | 同时证明问题存在、修复有效且没有回归 | 需要维护多类 JUnit 判定 |
| 全量再次确认目标测试 | 防止跳过或收集配置伪造全绿 | 全量测试必须额外解析目标结果 |
| 受信 DOCX 断言 | 将可确定的 Word 结构纳入自动证据 | 无法覆盖全部主观视觉质量 |
| 哈希绑定发布内容 | 防止验证后替换补丁或文件集合漂移 | 补丁组合和对账逻辑更复杂 |

## 8. 流程概览

```text
feedback(status=validating)
  -> reproduce_target：基线 + test patch
  -> validate_target：基线 + test patch + fix patch
  -> validate_full：基线 + test patch + fix patch + DOCX
  -> Controller 固定优先级计算 ValidationResult
  -> 校验补丁哈希、文件清单和工作区差异
       ├─ passed -> validated -> publishing -> Publisher
       └─ failed -> failed，保存报告并结束自动流程
```
