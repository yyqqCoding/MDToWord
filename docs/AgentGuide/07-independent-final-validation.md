# 07 · 独立终验:不信 AI 的自夸

> 上一章([06](06-repair-outcomes.md))讲了 AI 收场后的分流:修复成功会进 validating。
> 这一章讲 validating 之后那道最关键的闸——**独立终验(validate_final)**。
>
> AI 在上一章说"我修好了"——但这台机器从不轻信。修复成功只意味着"AI 自己车间里、跑 AI 自己
> 挑的那条测试,过了"。这一章,系统开三个**全新的容器**,从**锁死的那份源码**从头重跑,交叉
> 验证"AI 没自夸"。

## 1. 一句话:为什么 AI 说的"修好了"不算数

想一个问题:AI 宣布修好,凭的是什么?凭它在**自己车间**里,用**自己写的测试**,把目标测试跑绿了。
这中间有至少三个可以作弊或出错的口子:

1. **测试可能写得放水**——断言弱到"怎么跑都过",那"修好了"就毫无意义;
2. **修复可能只对这条测试有效**——换个输入就坏,或者把别的地方改坏了;
3. **AI 可能自我感觉良好**——它以为过了,其实只是日志长得像过了。

独立终验的设计目标,就是**把这三个口子全堵上**:用一套 AI **完全插不进手**的写死流程,从
**三个不同角度**重新证明一件事——

> **Bug 确实存在(基线必须失败),修复确实让它过了(目标必须通过),而且没把别的弄坏(全量必须
> 干净)。**

## 2. 终验在哪儿跑:三个全新的、一次性的容器

终验**不用** AI 跑过的那个车间(那个已经销毁了,而且 AI 在里面动过手脚的可能性本就存在)。
它开的是**三个全新的容器**,都基于**同一个锁死的快照**(第四章的 `base_sha`),从零搭起:

| 容器 | 工单(Job)类型 | 带什么 | 期望什么 |
|---|---|---|---|
| ① reproduce-baseline | REPRODUCE_TARGET | **只带测试补丁**,不带修复补丁 | **必须仍然失败**——证明 Bug 确实存在、测试不是白写的 |
| ② run-target-tests | VALIDATE_TARGET | 测试补丁 **+ 修复补丁** | **必须通过**——证明修复真的让这条测试绿了 |
| ③ run-full-tests | VALIDATE_FULL | 测试补丁 + 修复补丁,跑**整个后端测试集** | **必须干净**——证明没把别的地方改坏 |

三个容器各跑各的 pytest 命令,命令由 Job 类型**写死**,谁也改不了。每个容器跑完返回**可信的
结构化结果**(JUnit 摘要 + 容器工作区哈希),不是一大坨能被误读的日志。

> 为什么是"全新容器 + 锁死源码"?为了**可复现**。终验必须证明"这套补丁在这版代码上成立",
> 而不是"在某个谁也不知道的环境里碰巧成立"。三个容器环境完全一致、代码完全一致,唯一的变量
> 就是"带不带修复补丁"——这样才能干净地分离出"修复的功劳"。

## 3. 一个"验中验":Word 结构也要查

第 ②③ 个容器跑测试时,如果这次修复和**数学公式/表格结构**有关,测试里会带一个受信的
**DOCX 检查(Oracle)**:不只看"测试断言过了",还要真打开生成的 Word 文件,核对里面的结构
(公式是不是真的、表格是不是对齐)。这个检查是**受信回归测试**的一部分,它的结论由写死的断言
给出,模型改不了、AI 也注不进去水。

而且第 ③ 个容器的全量结果里,**必须再次证明那条目标测试被收集到并通过了**——防止补丁在某处
悄悄把目标测试跳过、"看起来全绿其实根本没测到"。

## 4. 终验结果怎么判:四个布尔值做与运算

三个容器跑完,本地代码把结果汇总成一个**验证结论(ValidationResult)**,判断逻辑是**写死的、
固定优先级的**——模型提供不了"passed"这个字段,它只能看结果:

```text
passed = ①基线仍失败(baseline_reproduction.expected_failure_observed)
      ∧ ②目标测试通过(target_validation.passed)
      ∧ ③全量测试干净(full_validation.passed)
      ∧ DOCX 检查通过(docx_validation.passed)
```

**四个条件缺一不可。** 哪一环不对,就按固定优先级记下第一个失败原因:

| 失败原因(failure_code) | 哪个容器露馅了 | 说明 |
|---|---|---|
| `baseline_reproduction_failed` | ① | 咦,基线竟然没失败?那要么测试写得太弱,要么 Bug 根本不存在 |
| `target_validation_failed` | ② | 修复没让目标测试绿——AI 自称的"修好了"是假的 |
| `skipped_tests_increased` | ③ | 全量里被跳过的测试变多了——可能在偷偷绕过什么 |
| `full_validation_failed` | ③ | 全量测试有失败/报错——把别处改坏了 |
| `docx_validation_failed` | ③(DOCX 检查) | 生成的 Word 结构不对 |

> 注意 ValidationResult 自己带一条**一致性守则**(代码里的 model_validator):如果 `passed` 和下面
> 四个子结果对不上、或者"passed 却带失败原因",这整个结论就会被判**非法**。也就是说,连"终验
> 的结论"本身都逃不过一致性校验——坏数据在这里根本活不下来。

## 5. 终验之外,还有两道"料"要查

三个容器跑完只是终验的**测试部分**。在宣布"验证通过"之前,还要查两样**静态的东西**:

1. **补丁组装一致性**:测试补丁和修复补丁被拼成一份"已验证补丁(validated patch)",重新算出它的
   哈希和改动文件清单,存进验证结论——以后发布时要拿这份存档对账,防止中途被人偷换;
2. **每个容器的工作区哈希**:容器跑完后,系统比对"容器里实际出现的改动"和"我们授权的改动"
   ——一旦发现多改了别的东西,直接判 `SECURITY_REJECTED`。

一句话:**终验既要"跑得对",也要"没乱动"。**

## 6. 通过 / 不通过,各自去哪

验证结论出来后,外层收场节点(finish_validation)读它,把反馈推进到下一站:

| 验证结论 | 反馈状态 | 去哪 |
|---|---|---|
| **通过(passed)** | validated → publishing | 交给发布器,准备发 PR(下一章) |
| **不通过(failed)** | failed | 收场。这次自动修复到此为止,留人工看验证报告 |

> 终验失败不是世界末日——它恰恰是这套系统"诚实"的体现:宁可让 AI 白忙一场,也**绝不放行一条
> 没被独立证明的修复**。失败的验证报告会存下来,将来人工可以拿着它判断"这条到底该不该人工修"。

## 7. 这一章的流程图

```text
finish_repair_success(反馈 → validating)
   │
   ▼
validate_final 节点:基于锁死快照,开 3 个全新容器
   │
   ├─ ① reproduce-baseline:只带测试补丁 → 必须仍失败(Bug 确实在)
   ├─ ② run-target-tests:测试+修复补丁   → 必须通过(修复真的有用)
   └─ ③ run-full-tests:全量后端测试集     → 必须干净(没改坏别处)
        │              └─ 附带:DOCX 检查(Word 结构对)+ 目标测试确实被收集
   │
   ▼
本地代码汇总(固定优先级,模型插不进手):
   passed = ① ∧ ② ∧ ③ ∧ DOCX
   │
   ├─ 哈希/改动文件对账 + 每个容器工作区哈希比对(防乱动)
   ▼
finish_validation
   ├─ 通过 → 反馈 validated → publishing → 下一章发 PR
   └─ 不通过 → 反馈 failed(留人工 + 验证报告)
```

## 8. 这一章出现的关键词速查

| 词 | 人话 | 对应代码/位置 |
|---|---|---|
| validate_final(独立终验) | 开三个全新容器交叉验证"AI 没自夸" | `graph.py` 的 `validate_final` 节点 |
| 三容器 | ①基线(必须仍失败)②目标(必须过)③全量(必须干净) | `reproduce-baseline` / `run-target-tests` / `run-full-tests` |
| ValidationResult | 汇总后的验证结论;passed 由四个子结果做与运算 | `agent/domain/repair.py` |
| DOCX Oracle | 受信回归测试里"真打开 Word 查结构"的检查 | 受信测试断言之 `trusted_docx_check` |
| 一致性守则 | 结论自带的 model_validator:对不上就整个判非法 | `ValidationResult.require_consistent_pass_state` |
| 已验证补丁 | 测试+修复补丁拼成一份,算好哈希和改动清单存档 | `compose_validated_patch` / `validated_patch_ref` |
| 工作区哈希比对 | 容器实际改动 vs 授权改动,不一致=SECURITY_REJECTED | `workspace_diff_sha256` 比对 |

**验证通过,就可以见人了。** 下一站是整台机器唯一能碰 GitHub 的环节——发布器把这条验证过的
修复变成一条 PR,端到维护者面前。
