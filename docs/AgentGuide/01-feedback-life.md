# 01 · 一份反馈的一生

> 如果你只读一章,就读这一章。它只讲故事,不解释名词;名词在
> [README 术语表](README.md)里都能查到。

## 故事的起点

一位用户在用扩展把网页内容转成 Word 时出了问题——表格乱了,或者某个公式直接让它报错,
或者整段转出来是乱码。扩展里有个"反馈"入口。用户把**出问题的那段 Markdown** 和一句
"转出来坏了,期望是 XXX" 提交上来。

在大多数产品里,这条反馈会进一个工单系统,等一个真人来看。但在这套系统里,反馈会走向一台
**自动修 Bug 的机器**。它在处理任何一件事之前,都先问一个根本问题:

> **"我凭什么相信这条反馈?"**

用户可能讲不清楚、可能描述错了、可能夹带一句想骗机器执行的操作(提示词注入),也可能根本
是垃圾消息。所以这台机器从头到尾的态度是:**先把用户给的所有文字当成"可能不怀好意的数据"
存起来,再用一套写死的流程小心地处理它。**

## 第一步:先存起来,再"签收"

反馈到达后,服务只做很基础的事:**做格式校验、限流(防止被刷)、脱敏(联系方式不进入后续任何
环节)、写进数据库**。这时候它的状态叫"待处理(pending)"。

数据库里躺着的反馈,不会立刻被处理。有一个叫 **Scheduler(轮询员)** 的后台循环,每几秒醒来
一次,**一次只认领一个任务**。认领不是随便把它捞出来,而是：

- 给这条反馈盖上"**当前归我处理**"的戳(随机认领牌 + 一个时间上限,叫租约/保质期);
- 为它建一条"**运行(run)**"记录:从这一刻起,这次处理有了一个唯一编号。

为什么要"一次只领一个"、还要带保质期?因为机器改的是**真仓库的代码**,如果两个进程同时处理
两条反馈、各自基于不同的代码版本改,改完一合并就互相打架。所以一次只处理一件,处理完再领
下一件。认领带"保质期"是为了防呆:万一处理到一半进程崩了,任务不会永远卡在"已认领"状态,
过期后会自动回到队列,由别人重新认领。

## 第二步:安检(Gate)——先判断要不要管

认领之后,流水线先把这条反馈送到安检口。安检员是一个**没有工具的 AI 模型**——它只能读文字、
做分类,没有任何能碰文件、跑代码、发消息的"手"。它要回答:

- 这条是正经 Bug 反馈,还是垃圾、无关内容?
- 里面有没有想骗它执行操作的提示词注入?
- 问题是出在**后端转换**(我们负责的)、前端扩展,还是只是一句"想要个新功能"?
- 信息够不够?

安检员把结果吐成一个**严格的表格**(意图、类别、可信度……),然后再由一段**写死的本地守则**
(Policy)检查一遍——AI 自己的判断不算数,必须过本地守则这一关才算定论。

根据定论,反馈被分成几条路:

| 安检结果 | 处理方式 |
|---|---|
| 无关 / 垃圾 | 直接结束,标记"已拒绝" |
| 夹带注入 / 想越权 | 直接隔离(quarantine),**一个工具都不让它碰** |
| 信息不足 | 转人工(needs_human),等人来看 |
| 功能需求、前端/扩展问题 | 走另一条支路:整理成一条脱敏的 GitHub Issue,让维护者看 |
| **正经的后端转换 Bug** | **唯一能进自动修复链的路** ↓ |

（如果另外还有一条"处理中"的反馈,内容几乎一模一样,也会被识别出来,直接标记为重复、不为它开工——既省模型钱,也避免对同一次故障发出两条一样的修复。这条支路在[03](03-gate-classification.md)里细讲。）

## 第三步:把代码"锁死"在一个版本上

进入自动修复链后,第一件事**不是**让 AI 看 Bug,而是先去 GitHub 把 **main 分支当前那份源码
整个复制一份只读副本**,记下当时的提交号 `base_sha`。

为什么?假设 AI 第一天写测试说"这段代码会坏",你修到第三天,期间 main 已经被人改过了——那
"它确实会坏"这个结论还成立吗?不一定。所以必须**锁死**:这次修复的全部工作(复现、修、验)
都在这份固定副本上进行。这也让后续每一步都可以追溯:你永远知道当时测的是哪一版代码。

## 第四步:AI 上场——先证明 Bug 真的存在

现在轮到"干活的人"了。这段是整条流水线里**唯一让 AI 自由发挥的地方**,也是这套系统最核心
的设计,值得单独一章([05](05-repair-agent-deep-dive.md))讲。这里先讲大意。

AI 开始干活前,系统先做一个**免费的小实验**:把用户那段 Markdown 原样跑一遍转换,看它是不是
**直接崩溃**。

- 如果直接崩溃 → 那太好了,问题很硬:系统直接据此写一条回归测试,AI 的任务变成"把崩溃修好"。
- 如果没崩溃,只是"结果不对" → 那 AI 就得自己先想清楚"怎么证明它不对":根据用户描述写一条
  **能反映这个 Bug 的测试**,然后在这份没修过的代码上真跑一遍,**亲眼看到它失败**。

这一步叫"复现(reproduce)"。它的意义是:**AI 不能凭用户的描述就动手改代码**。改之前必须先有
一条"现在确实会失败"的测试攥在手里——这既是给 AI 自己看的"敌人长什么样",也是将来验证
"我修好了没有"的标尺。

复现很关键的一个点:如果写了好几条测试都**没法让它失败**,AI 必须停下来承认"我复现不出来",
而不是假装这是个 Bug。可能是测试没写对,也可能是用户描述根本站不住。

## 第五步:AI 修复——在隔离容器里反复试

复现成功后,AI 进入修复模式。它的工作方式是"看代码 → 提修改建议 → 去容器里真跑一遍 →
看结果",循环往复:

1. 搜索、阅读相关源码;
2. 提交一个**最小修复补丁**;
3. 把补丁送进**隔离容器(沙箱)**跑那条测试;
4. 看结构化结果:过了?没过?为什么?
5. 没过就回去改,过了就宣布"我修好了"。

这里每一步都被套上了缰绳:AI 提交的补丁**只能改后端两个白名单文件**;容器是**没网、非管理员、
跑完即毁**的一次性环境;AI 想验证只能挑"我要跑当前这个测试",不能挑命令、不能挑环境。

**AI 说"我修好了"也不算数。** 它只是通过了"目标测试"。外层系统还要做下一步的独立复核。

## 第六步:独立终验——不信 AI 的自夸

AI 宣布修好后,系统**不直接发 PR**,而是开三个**全新的容器**,从那份锁死的代码重新来一遍:

1. 只带"测试补丁"跑一遍基线 → 必须**仍然失败**(证明 Bug 确实存在,测试没白写);
2. 带上"测试补丁 + 修复补丁"跑目标测试 → 必须**通过**(证明修复确实让这条测试绿了);
3. 跑**整个后端全量测试** → 必须**没有回归**(证明没把别的地方改坏)。

另外还要查这次修复生成的 Word 文件结构、确认改动只碰了允许的文件、补丁的哈希和记录对得上。

只有这四条证据都齐,才算"验证通过"。这套独立验证**完全在本地代码手里,模型一点插不进手**——
它是防"AI 自卖自夸"的最后一道闸。

## 第七步:发布——变成一条 GitHub PR 交给真人

验证通过后,流水线的**发布器**(整个系统里唯一能碰 GitHub 的环节)创建一条 PR,把**脱敏后**的
问题摘要、四条验证证据、改了哪些文件、花了多少钱一起写进 PR 描述。

到这里,机器的工作就结束了。**PR 不会自动合并**。真正上线要靠一个真人——维护者——去 review
代码、合并、部署,最后拿用户那段原始 Markdown 在真实 Word 里肉眼确认一遍。这才是闭环:
机器把"一个 Bug 的完整修复方案 + 全部证据"端到真人面前,人拍板。

## 分支剧情:功能需求 / 前端问题

如果安检时发现这不是后端 Bug,而是"想要个新功能"或"前端扩展坏了",系统**不会**进自动修复链
(因为这条链只能改后端两个文件,管不了这些)。它会走 Issue 支路:把反馈整理成一条**脱敏的
GitHub Issue**——只留摘要,不泄露用户原文和联系方式——交给维护者去排期。

## 中间出错了怎么办

这台机器为自己的健壮性设计了大量保险,值得单独一章([09](09-failures-and-recovery.md))讲。
先记住几个最重要的原则:

- **每一步都有存档(checkpoint)**:进程死了可以从存档点接着跑,而不是从头再来;
- **失败要分门别类**:只是网络抖了一下(重试)和"权限不够"(别重试,认栽),是两种完全不同的
  处理;
- **预算上限**:AI 不是无限试的。模型调用次数、容器时长都有限额;用完就停,不会无休止烧钱。

## 现在你有了全局印象

一句话总结这台机器:

> **安检 → 锁版本 → 复现 → AI 修复 → 独立复核 → 发 PR 给真人。**
