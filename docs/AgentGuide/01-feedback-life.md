# 01 · 端到端流程与核心设计

本文从一次反馈进入系统开始，说明它如何经过接收、路由、源码准备、复现、修复、独立验证
和发布，最后进入明确的业务终态。重点不是复述每个类和函数，而是说明阶段之间的边界、
证据如何传递，以及这些边界为什么必须存在。

具体状态、字段、工具参数和权限规则见
[AgentRequirements](../AgentRequirements/README.md) 及其子文档。

本文首次引入英文术语时，会同时给出中文含义和它在本系统中的职责；后续保留代码中的
英文名称，必要时继续附带中文简称。状态值、字段名和工具名使用代码原名，解释其含义时
不把它们当作普通英文阅读。

## 1. 问题定义

用户通过浏览器扩展提交 Markdown 和问题描述。反馈可能属于以下几类：

- 可以自动处理的后端转换缺陷；
- 功能需求或前端/扩展问题；
- 无关、信息不足、重复或包含越权意图的内容。

自动处理后端缺陷时，系统还必须解决四个问题：

| 问题 | 直接风险 | 设计响应 |
|---|---|---|
| 反馈不一定可信 | 模型被错误描述或提示词注入影响 | 反馈分类器（Gate）只做结构化分类，本地策略校验器（Policy）决定路由 |
| 源码会持续变化 | 复现、修复和终验可能不基于同一版本 | 每个处理运行（run）固定基础提交 SHA（base_sha）和源码快照 |
| 模型需要探索代码 | 固定步骤无法覆盖未知缺陷 | 只在受限的观察—行动工具循环（ReAct）内层循环中探索 |
| 自动执行可能产生副作用 | 测试或补丁可能越权、破坏主机或重复发布 | Policy、隔离执行环境（Sandbox）、独立验证和发布器（Publisher）共同控制 |

因此，系统的基本原则是：模型负责提出候选动作，受信代码负责授权、执行、验证和发布。

## 2. 总体流程

~~~text
浏览器扩展
  -> 反馈接口（Feedback API）
       -> Supabase（业务状态存储）：feedback（反馈记录）= pending（待处理）
            -> 调度器（Scheduler）：claim（认领）+ run（一次处理运行）
                 -> 外层流程编排框架（LangGraph）
                    -> 反馈分类器（Gate）/ route（路由）
                       |- reject（拒绝）/ quarantine（隔离）/ human（人工处理）
                       |- Issue 发布器（Issue Publisher） -> issue_opened（Issue 已创建）
                       +-- 源码快照（source snapshot）
                            -> 修复代理（Repair Agent）
                               -> 复现（reproduction）
                               -> 修复（repair）
                            -> 独立验证（independent validation）
                               |- failed（验证失败）/ budget_exhausted（预算耗尽）
                               +-- PR 发布器（PR Publisher） -> pr_opened（PR 已创建）
~~~

外层和内层各自负责不同层次的控制：

~~~text
外层：start_gate -> classify_gate -> route_feedback
      -> prepare_source -> repair_agent -> validate_final -> publish

内层：搜索/读取源码（search/read source）
      -> 提交测试补丁（test patch）或修复补丁（fix patch）
      -> 执行固定的沙箱任务（Sandbox Job） -> 观察结果（observe result）
      -> 继续、完成或报告阻塞（continue, complete, or report blocked）
~~~

外层流程图（Graph）决定业务阶段和不可跳过的节点；内层 Agent 只决定当前阶段的下一项已授权动作。
模型不能跳过源码快照、基线复现、独立验证或发布前检查。

## 3. 接收、认领与运行所有权

### 3.1 反馈接口（Feedback API）只负责登记

入口 API 对反馈执行大小、格式和入口限流校验，并将通过校验的内容写入 Supabase。
它不调用模型、不读取源码、不执行 Sandbox，也不直接决定反馈是否属于后端缺陷。

这样划分的原因是将公网入口与高权限执行面隔离。入口只产生待处理业务记录，
后续处理由私有 Scheduler 和 Controller 负责。

### 3.2 调度器（Scheduler）先恢复，再领取新任务

Scheduler 每轮执行以下顺序：

1. 查找仍处于可恢复状态的活动处理运行（run）；
2. 如果存在，使用原 run_id 和检查点（checkpoint）继续执行；
3. 如果不存在，再通过数据库原子操作领取新的 pending 反馈；
4. 为本次领取绑定认领令牌（claim token，用于证明当前运行拥有反馈更新权）和
   认领租约（lease，规定本次认领的有效时间），并启动控制器（Controller）。

生产执行工作进程（Worker）和 Scheduler 按单并发运行。claim token 用于条件更新，lease 用于避免进程
异常退出后任务永久停留在已领取状态。lease 过期并不意味着可以无条件重做；数据库还会
结合领取次数和终态策略判断是否允许再次处理。

### 3.3 反馈记录（Feedback）状态与运行记录（AgentRun）状态分离

Feedback 状态表达业务生命周期，例如 pending、reproducing、validating、pr_opened；
AgentRun 状态表达一次执行的阶段和结果。内层消息、工具调用和恢复信息则保存在私有
检查点（checkpoint，用于中断恢复的持久化记录）中。

分离的好处是：

- 业务页面和调度逻辑不依赖完整模型消息；
- 内层上下文压缩不会覆盖业务事实；
- 同一个 run 恢复时可以继续原会话线程（thread，内层 Agent 的可恢复执行线程），而不是创建新的执行身份；
- 外部观测系统不可用时，不会改变业务状态。

## 4. 反馈分类器（Gate）与反馈路由

### 4.1 反馈分类器（Gate）只分类，不执行动作

Gate 接收反馈的最小必要字段，返回严格结构化结果，包括问题区域、类别、风险和建议
路由。Gate 不注册任何工具，因此不能读取文件、运行代码、修改状态或创建 GitHub 对象。

在 Gate 结果写入制品存储（Artifact，用于保存大对象和结果引用）后，外层 Graph 由本地
策略校验器（Policy）再次校验并执行路由：

| 路由结果 | 后续处理 |
|---|---|
| 无关或垃圾 | 进入 rejected_irrelevant |
| 提示词注入、越权或安全风险 | 进入 quarantined_security，不进入修复链 |
| 信息不足、无法可靠判断 | 进入 needs_human |
| 功能需求或前端/扩展问题 | 生成脱敏 Issue（GitHub 问题或需求单），进入 issue_opened |
| 相关且信息充分的后端缺陷 | 进入源码准备和自动修复链 |
| 重复反馈 | 进入 duplicate，不重复启动修复 |

### 4.2 为什么要将模型分类与本地路由分开

分类问题适合使用模型处理，因为自然语言反馈的表达方式不固定；权限和状态问题不适合
交给模型，因为模型不能成为自己的授权者。

因此，模型只提供路由信号，本地代码负责：

- 规范化和校验结构化字段；
- 检查重复反馈；
- 将结果映射到有限的业务状态；
- 拒绝模型声称拥有的额外权限。

这个边界使 Gate 可以使用模型的语义理解能力，同时不让分类错误直接扩大为文件、执行或
发布权限。

## 5. 固定源码版本

进入后端自动修复链后，控制器（Controller）首先读取 GitHub 主分支（main）的完整提交
SHA，即基础提交 SHA（base_sha），并取得该版本的源码归档。归档写入当前 run 的工作区后，
系统保存快照哈希和源码快照引用（source snapshot reference）。

后续测试补丁、修复补丁、沙箱执行任务（Sandbox Job）和最终验证都引用同一个源码快照。
Artifact 只在状态中传递引用，补丁、JUnit、日志和验证结果等大对象不直接写入外层流程状态
（Graph State）。

### 5.1 固定版本解决什么问题

如果不固定版本，可能出现以下情况：

1. 基线测试针对提交 A 失败；
2. 修复测试针对提交 B 通过；
3. 最终验证针对提交 C 执行；
4. 发布时无法证明补丁究竟基于哪一版代码成立。

固定 base_sha 后，整个 run 的证据都绑定到同一版本，结果可以复现、审计和比较。
发布前仍需检查 main 是否已经前进；如果已经变化，系统进入基础版本过期（stale_base）
处理，不直接把
旧版本上验证过的补丁当作当前版本的补丁发布。

## 6. 复现与修复

### 6.1 先执行转换探针（conversion probe）

修复代理（Repair Agent）启动前，系统在固定快照上执行一次不调用模型的
转换探针（conversion probe，即判断 Markdown 是否在转换阶段直接抛错的确定性检查），
判断用户提交的 Markdown 是否在转换阶段直接抛错。

结果决定复现入口：

| 转换探针结果 | 复现方式 | 原因 |
|---|---|---|
| 转换直接抛出错误 | 控制器（Controller）生成固定转换回归测试 | 系统已经获得确定性的失败信号 |
| 转换成功但结果不符合反馈 | 修复代理（Agent）设计语义回归测试，并在基线运行 | 需要将用户的主观描述转化为可验证断言 |
| 无法形成稳定测试或无法复现 | 结束为 cannot_reproduce 或 needs_human | 不在证据不足时猜测并修改代码 |

### 6.2 内层修复代理（Repair Agent）只在有限范围内探索

复现和修复阶段使用一个基于工具循环构建组件（create_agent）的内层
观察—行动循环（ReAct，模型根据观察结果选择下一项工具动作）。典型循环是：

1. 在白名单源码中搜索和读取相关内容；
2. 提交测试补丁（test patch）或修复补丁（fix patch）；
3. 调用当前阶段唯一允许的沙箱执行任务（Sandbox Job）；
4. 读取结构化执行结果；
5. 继续调整、完成阶段，或报告稳定的阻塞原因。

工具集合、阶段可见性、路径白名单、补丁大小、测试选择器、预算和完成条件均由本地代码
控制。模型不能提供命令字符串、任意工作目录、网络地址、凭据或新的工具名称。

复现阶段只能提交和验证 test patch；只有基线复现被受信结果确认后，修复阶段才允许提交
fix patch。这个顺序保证修复不是对用户描述的盲目响应，而是对一个已确认失败的测试
进行最小修改。

### 6.3 隔离执行环境（Sandbox）是执行边界，不是模型边界

沙箱执行工作进程（Sandbox Worker）接收结构化执行任务（Job），在固定镜像和一次性容器中执行
固定命令参数（argv）。容器无网络、非 root、限制 CPU/内存/进程数，执行后销毁临时
工作区。

模型不能修改 Job 内容。这样做的取舍是牺牲一部分临时实验的灵活性，换取：

- 可审计的执行命令；
- 可重复的运行环境；
- 对宿主机、凭据和外部网络的隔离；
- 对重复请求进行幂等处理的能力。

## 7. 独立验证与发布证据

Repair Agent 只能证明“当前目标测试在当前循环中通过”。它不能直接证明补丁没有削弱
测试、没有破坏其他功能，也不能改变外层发布条件。

候选修复完成后，外层流程图（Graph）在全新的 Sandbox 中重新执行：

1. 只带测试补丁执行基线，必须按预期失败；
2. 带测试补丁和修复补丁执行目标测试，必须通过；
3. 带完整验证补丁执行全量测试，必须通过；
4. 对生成的 Word 文档执行受信结构检查（DOCX 检查），并确认补丁文件、路径和哈希一致。

四类证据由本地验证器（Validator）汇总。只有全部满足，反馈记录（Feedback）才能进入 publishing；
任一证据失败都进入明确的 failed 或其他终态，不能由模型解释为“实际上已经修好”。

发布器（Publisher）在创建 PR（Pull Request，代码合并请求）前再次检查：

- base_sha 和源码快照哈希；
- 已验证补丁哈希（validated patch hash）和授权修改文件；
- 验证结果引用；
- 脱敏后的 PR 内容；
- 外部仓库中是否已经存在相同的发布副作用。

Publisher 只创建 PR 或 Issue（GitHub 问题或需求单），不合并、不部署。维护者负责代码
审查、合并和真实 Word 视觉确认，形成自动验证与人工判断之间的最后边界。

## 8. 失败、恢复与终态

系统不把所有异常都处理成同一种重试。失败首先按原因区分：

- 临时模型或网络传输失败：按重试策略（Retry Policy）有界重试；
- 幂等 Sandbox 请求的临时传输失败：复用同一任务标识（Job ID）重试；
- 参数、前置条件或测试问题：返回结构化错误，由 Agent 在当前循环修正；
- 越权、安全、认证和永久配置错误：立即终止，不重复尝试；
- 模型、工具或 Sandbox 预算耗尽：进入预算耗尽（budget_exhausted）；
- 进程重启：从外层数据库状态和内层 checkpoint 恢复原 run。

恢复设计必须同时满足两个条件：

1. 已经完成的补丁、Sandbox 和发布操作不被无条件重复执行；
2. 恢复后的执行仍使用原来的 base_sha、run_id 和线程标识（thread_id，内层 Agent 会话线程标识），
   以及累计预算。

因此，检查点（checkpoint）解决“从哪里继续”，幂等标识解决“已经做过什么”，业务状态解决
“当前是否允许继续”。三者不能互相替代。

## 9. 本章结论

一次反馈的完整处理链可以概括为：

~~~text
登记并认领
  -> 结构化路由
  -> 固定源码版本
  -> 基线复现
  -> 受限探索与修复
  -> 独立验证
  -> 创建 PR / Issue
  -> 维护者审核和上线
~~~

这条链路的核心不是让模型承担更多工作，而是把模型的探索能力放在明确的受信边界内：

- 模型负责理解反馈、搜索源码和提出候选动作；
- Controller 和 Graph 负责业务阶段；
- Policy 负责授权和状态条件；
- Sandbox 负责隔离执行；
- Validator 负责证据；
- Publisher 负责有限的外部写入；
- 维护者负责最终合并、部署和真实效果确认。
