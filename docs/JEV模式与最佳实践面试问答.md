# JEV 模式与最佳实践面试问答

这份文档用面试问答的方式说明 JEV 在 MDToWord 反馈 Gate 中的定位、使用方法、常见问题，以及这次“三级标题无法识别”反馈的修复过程。

## 一、JEV 模式是什么？

**问题：JEV 是什么？它和普通的大语言模型分类有什么区别？**

**回答：** JEV 是 TypeSafe 提供的结构化判断模型，我们当前使用的模型是 `jev-1.13.0`。它的特点不是让模型自由生成一段分类说明，而是先给模型一份结构化状态，再提出若干个带有明确选项和判断标准的问题，最后得到可校验的 choice、score 或布尔结果，以及对应的概率和置信度。这样做的价值是把语言理解交给模型，把状态流转、权限和路由交给本地系统，模型只负责回答问题，不能自行决定是否创建 Issue、修改代码或发布结果。

**问题：JEV 在我们的系统里处于什么位置？**

**回答：** JEV 是反馈进入 Agent 流程前的 Gate 分类器，主要判断反馈是否属于 MDToWord、是否存在提示注入、是否混合了多个诉求、属于缺陷还是功能需求、涉及后端还是扩展，以及信息是否足够继续处理。JEV 返回结构化判断后，本地 Policy 再根据安全优先级、相关度、信息完整度和阈值决定拒绝、转人工、进入 Issue 流程，还是进入沙箱复现流程，所以 JEV 是判断组件，不是整个 Agent 的决策者。

**问题：JEV 的输入和输出应该怎样理解？**

**回答：** 输入由可信的产品上下文和本次用户 state 组成，用户 state 保存反馈类型、问题描述和完整 Markdown，问题定义再明确指出需要判断哪些字段和标准。JEV 直接理解原始 Markdown，不依赖 Python 预先生成的语义 facts；输出则是多个独立问题的结构化答案。我们保留 JEV 的概率、置信度和专用 routing score，但不会把它和旧 Gate 的 relevance 当成同一个数值，也不会让模型输出 Issue 标题、摘要或执行指令。

**问题：当前实际使用的是哪个模型？**

**回答：** 生产环境默认使用 TypeSafe 的 `jev-1.13.0`，通过 TypeSafe 的 `systemone` 契约调用，具体地址和密钥由部署环境注入。运行记录会保存最终实际使用的 provider 和 model，页面应该展示这两个真实字段，这样排查时能确认请求确实走了 JEV，还是因为 JEV 不可用而走了 `gate-v10` 回退路径。

**问题：JEV 是否需要像普通聊天模型一样传完整上下文？**

**回答：** 不需要传完整的聊天历史，但也不是只传一句问题。JEV 的一次请求是独立的，可信产品上下文和用户 state 共同构成这次判断所需的上下文，`questions` 是针对它们提出的结构化问题；模型不会自动记住上一轮请求，也不会从其他对话中补齐内容。因此我们要把产品说明、反馈类型、问题描述和完整 Markdown 一次性传入，再让 JEV 回答 related、intent、area、sufficient 等问题。

**问题：JEV 的 questions 是不是可以看成系统提示词？**

**回答：** 可以把 questions 理解成比普通系统提示词更结构化的判断契约，但不能把它当成只包含规则的提示词。每个问题有自己的类型、说明和选项标准，JEV 会在同一个 state 上分别回答这些问题；如果只传问题而不传足够的 state，模型就没有判断依据，结果很容易变成 unknown 或信息不足。当前实现为了兼容旧 Gate 仍会组装一份通用系统消息，但 JEV 路径真正解析的是用户数据里的结构化 state，旧的 `gate-v10` 才依赖那份自由文本系统提示词。

## 二、我们应该怎样正确使用 JEV？

**问题：设计 JEV 输入时最重要的原则是什么？**

**回答：** 输入要让模型看到产品边界和本次反馈，同时让每个问题都能被单独回答。我们保留原始反馈字段和完整 Markdown，再提供一段固定的产品说明；问题中直接引用产品上下文和用户 state，选项使用互斥且可观察的标准，避免让模型猜测产品职责。原始 Markdown 仍然保留给后续沙箱验证，Gate 只负责判断是否具备进入下一阶段的条件。

**问题：为什么不再由 Python 预先计算标题等事实？**

**回答：** 这些内容本身就在完整 Markdown 中，JEV 可以直接理解标题、表格、公式和文档结构；把它们提前转换成 facts 会增加一层重复逻辑，也可能让输入结构变得复杂。Python 继续负责空值、长度和重复等入口保护，JEV 负责理解原始内容，本地 Policy 负责把判断转换成路由。

**问题：JEV 的置信度低时应该怎么处理？**

**回答：** 置信度和概率只能作为路由信号，最终仍由本地 Policy 决定。安全判断不明确、反馈混合、归属不明确或信息不足时转人工；明确属于产品且信息充分的后端缺陷才进入沙箱；与产品无关的反馈直接拒绝。JEV 请求失败才使用完整的 `gate-v10` 回退，低置信度本身不等于 JEV 失败，也不应该因为低置信度就悄悄换成另一个分类器。

**问题：在本项目中，哪些输入细节最容易影响结果？**

**回答：** 最容易出问题的是把用户原文压缩得过度、只传问题描述而丢掉 Markdown、产品上下文写得过于简单，以及没有说明后端输出问题和扩展界面问题的区别。对于标题、表格、代码块等格式反馈，必须保留完整原文；对于区域判断，要明确只有用户提到浏览器扩展、前端预览或 UI 时才归到扩展，明确的 Markdown 转 Word 或 DOCX 输出问题才归到后端，否则保持未知。

**问题：使用 JEV 时有哪些常见坑？**

**回答：** 一是把 JEV 的分数直接当成旧 Gate 的 relevance，导致阈值含义混乱；二是让模型自己决定权限、创建 Issue 或发布结果；三是把“信息不足”误判成“服务不可用”，从而错误回退；四是生产环境漏装 `typesafe-sdk`、模型配置和页面展示不一致；五是增加大量回退原因或调试消息，反而让运行记录偏离用户真正关心的分类结果。正确做法是固定输入边界、固定本地路由规则、锁定运行依赖，并展示真实 provider/model。

**问题：为什么页面必须展示真实模型？**

**回答：** 同一份反馈可能经过 JEV，也可能因为超时、鉴权、协议或依赖问题回退到 `gate-v10`。如果页面只展示“分类完成”，我们无法判断实际走了哪条路径，也很难解释一次错误路由。保存并展示最终响应中的 provider 和 model，可以让用户和维护者直接确认本次运行的模型来源，同时保留 JEV 的 routing score 或旧 Gate 的 relevance 作为对应路径的诊断信息。

## 三、这次问题是如何修复的？

**问题：这次“无法识别三级标题”为什么会错误转人工？**

**回答：** 原来的输入虽然包含反馈描述和文档内容，但给 JEV 的判断上下文不够明确，模型没有稳定地把“三级标题”和“Markdown 转 Word 的后端输出”联系起来，信息充分性和处理区域可能因此变得模糊。对于一个实际导出可以正常显示三级标题的问题，正确流程应该是进入沙箱验证，验证后给出无法复现，而不是在 Gate 阶段直接转人工。

**问题：我们具体改了什么？**

**回答：** 我们把 JEV 输入收敛为固定的 MDToWord 产品上下文加原始用户 state，并把每个判断问题改成引用这两部分，使用清晰选项和可观察标准；同时明确 Markdown 转 Word 输出问题属于后端、包含具体问题描述和 Markdown 时通常已经满足沙箱验证的最低信息。运行时显式使用配置的 JEV 模型，部署锁中补齐 `typesafe-sdk`，并把实际 provider/model 写入运行记录和页面展示。原有安全判断、本地 Policy 和 `gate-v10` 回退机制继续保留。

**问题：为什么这次真实反馈已经恢复正常？**

**回答：** 新的输入让 JEV 能直接看到 MDToWord 的产品边界、用户描述和完整 Markdown，因此可以理解“无法识别三级标题”是生成 Word/DOCX 的后端输出问题，并判断信息足够交给沙箱，而不是把它当成需要人工澄清的模糊反馈。你提交的运行记录已经证明这条路径恢复正常，后续沙箱验证导出结果后即可得到无法复现的结论。

**问题：以后遇到类似问题，应该怎样排查？**

**回答：** 先看运行页面显示的真实 provider 和 model，确认请求是否走了 `jev-1.13.0`；再看 JEV 的结构化判断、routing score 和本地路由结果，判断是输入理解问题、策略阈值问题，还是服务回退问题；最后结合沙箱的实际导出结果确认是否可复现。这样可以把模型判断、系统策略和业务验证分开定位，避免看到“转人工”就直接怀疑导出能力或盲目回滚模型。

## 四、这次反馈的真实输入前后对比

**问题：一开始我们实际给 JEV 输入了什么？**

**回答：** 原始输入的状态只有三个字段：`feedback_type`、`description` 和 `markdown_content`。以这次真实反馈为例，核心内容是 `feedback_type: "bug"`、`description: "无法识别三级标题"`，Markdown 内容中包含 `### 7.1 双E3连接酶策略（2.2已提及）`，完整 Markdown 会原样保留并传入。与此同时，问题定义比较宽泛：相关性问题把产品、导出、扩展和界面混在一起，区域问题只说“哪个产品区域”，信息充分性只问“是否有具体问题和相关输入”，标题类别只说“DOCX heading output is wrong”。也就是说，JEV 看到了原文，但没有被明确告知这是 MDToWord 后端转换、`###` 是可识别的三级标题，以及只要有可观察的输出症状和非空 Markdown 就可以进入沙箱。

**问题：优化后实际给 JEV 输入了什么？**

**回答：** 优化后的输入由固定的 MDToWord 产品上下文和用户 state 组成。用户 state 的核心内容是 `feedback_type: "bug"`、`description: "无法识别三级标题"`，以及包含 `### 7.1 双E3连接酶策略（2.2已提及）` 的完整 Markdown；产品上下文说明 MDToWord 的输入、输出、后端范围和扩展范围。问题定义改成了字段化标准：相关性需要结合产品上下文和用户 state 判断，区域只有明确的转换输出问题才归 backend、明确的扩展或 UI 问题才归 extension，信息充分性明确规定具体输出症状和非空 Markdown 通常足够进入 Sandbox，类别判断直接使用完整 Markdown 识别标题问题。

**问题：前后两次输入的根本差别是什么？**

**回答：** 原来的输入只有用户 state，模型需要自己推断产品边界；优化后的输入是“可信产品上下文加原始用户 state，再用明确问题约束判断”。这样 JEV 可以从完整 Markdown 中自己识别三级标题，从产品上下文中理解这是 Markdown 转 Word/DOCX 的后端能力，再由本地 Policy 决定进入沙箱或人工，最终这条反馈才能稳定得到无法复现的结论。
